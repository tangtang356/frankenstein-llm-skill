# 阶段3B分支：从缺失后端到完整可用组合

仅在选定引擎/模型需要新增设备后端、大量算子或架构支持时读取。普通安装与已有实现的小修仍走原流程。用户明确要求移植指定引擎时，交付目标包含该引擎与能力，不用另一个现成框架替换后宣称完成。

本分支也以[跨仓库缝合](cross-repository-composition.md)为先：宿主缺后端或算子，不代表需要自己重写。先检查其他仓库的速度来源、可复用机制及依赖，按[快因分析与硬件移植](cross-repository-composition.md#找到快的原因再决定如何移植)设计目标设备实现。有现成代码则接入；没有目标设备版本则改写所需kernel及配套，不把薄层适配当限制。所有新增实现都应服务于具体机制或必要能力，避免脱离目标重造整套引擎。

## 1. 先把需求映射到真实源码

固定源码来源、commit及权重revision；有官方与镜像时核对差异。官方暂不可读可继续基于固定镜像审计、整理接口和实现缺口，记录来源未对齐；不能宣称已核实官方当前版本，未满足的版本要求在正式基线前补齐。

从真实调用链映射设备接口、调度、模型容器/量化、架构插件、算子分派、内存/专家供给、KV/混合状态、原生投机、多模态及服务协议。逐模块记来源、直接复用、接口适配、剩余缺口及依赖；需要重写/新增的部分说明现成实现为何不能覆盖，只补必要范围；用户要求的功能缺口标待实现，不能写“不适用”来减范围。源码目录名与规划目录分开，不假造已存在的CUDA实现。

按用户要求产出架构、迁移映射、算子矩阵、内存预算和测试计划；没有指定格式时用现有工程文档即可。技能提倡一份接续记录不限制用户指定的研发文档；接续说明引用这些文件，不复制整套内容。

## 2. 在完整部署前，验证复用模块与必要补齐

“先完整部署，再做短ms优化”指整套部署的性能阶段，**不禁止阶段3B的编译、算子数值对照、局部微测和模块集成**。prefill、视觉和投机状态的基础实现属于完整部署，不得因“prefill专项最后做”而延后它们的实现。

按实际依赖推进：

| 集成里程碑 | 必要验证 | 能报告的完成范围 |
|---|---|---|
| 工具链和设备运行时 | 目标架构最小编译/设备执行，内存、stream/event、异步复制及错误路径 | 后端基础能力；不能称模型已运行 |
| 算子与状态基础 | 实际dtype/shape的参考数值、量化scale/旋转/码本、布局、同步和状态生命周期 | 对应算子可用；host参考不能冒充GPU实现 |
| 架构最小集成 | 加载真实容器，按依赖接通prefill/decode、原生投机、视觉及协议 | 已接通组件；仅文本或无投机版本可作中间里程碑，不能代替最终组合 |
| 多卡与资源整合 | 用户要求的并行路线、专家供给、跨卡状态/通信、逐卡和主机预算 | 该并行组合可运行；不能把单卡或TP基线冒称混合并行已完成 |
| 完整组合放行 | 所有要求的组件实际生效、短通路与相关状态检查完成，入口指向候选组合 | 阶段3B完成，可以进入阶段4整套基础ms优化 |

依赖满足的模块可并行开发；真实GPU测试按资源窗口串行或按预算执行，不能让多项测试争抢设备而误判性能。已有生产服务时使用独立分支、构建、库、配置和测试入口；独立目录不等于GPU资源隔离，不覆盖生产环境或为测试擅自停业务。无实机条件时继续源码/host参考工作，把设备编译、数值与性能检查留为明确待验证项，不伪造通过。

模块失败时保存直接错误和最小复现，修复该依赖并继续其他独立工作；参考路径可用于定位，但不能作为用户要求的GPU实现或完整性能结果交付。最终能力不缩水，不等于所有模块必须一次写完才允许测试。

## 3. 从真实分派条件设计正确性用例

短请求可能只覆盖一种路径。检查prefill与decode、单token与批量、投机提交/拒绝、页面/块边界、稀疏选择阈值、多卡路由、图片与文本混合路径。只增加能触达本次实现分支的最小用例，不扩成前期全窗口性能压测。

例如某模型在短上下文走dense attention，长度超过阈值才启用稀疏索引：短代码通过不能证明索引路径正确。阶段3B可使用阈值附近的受控张量或最小请求验证分支与数值；阈值来自当前源码/metadata，不硬编码历史案例值。真正的长上下文速度优化仍在阶段5。

原生MTP、独立Draft/Verify和其他投机路径分别核对训练/运行结构、history/draft/verify、接受和回滚语义。案例里的DSpine、DFlash或某个K不是替换模型原生投机结构的授权。

## 4. 资源预算必须覆盖加载过程和运行过程

逐设备核算主干、常驻/热专家、KV和混合状态、嵌入/特殊表、MTP、视觉、Graph及临时空间；主机核算冷权重、映射与实际副本、pinned staging、加载峰值、NUMA和系统余量。明确每项是常驻、按需调入还是分块处理，不重复统计同一权重。

文件大小减去总显存不是主机RAM预算，也不能证明可运行。混合格式逐tensor核对，尤其保护专家、大型N-gram表、尺度和非专家组件；不把全部权重解压或重新量化作为默认兼容办法。可行计算转换需保留用户要求的容器和量化语义，并用参考数值验证。

## 5. 接回阶段4—10并完成工程目标

完整组合形成后固定模型、量化、原生投机深度和能力，依次做短ms/传输等待、长上下文与缓存、用户指定任务、适用的K调优、正式对标、按需prefill专项及最终质量。模块微测、短整合反馈和最终统计比较分开，不给每个研发提交安排全套A/B。

用户目标是推理引擎本身时，已确认的工程测试计划可以作为指定任务和完成条件：例如文本、原生图片、MTP状态、工具/流式、并行调度和规定负载。不必再强迫用户提供另一个聊天业务；未明确的关键使用条件再询问，继续不依赖它的研发。

单路与并发分别验收。用户明确要求4路/8路时，最终需要真实重叠请求、排队、每请求延迟、总吞吐、缓存与资源稳定性；不能用多卡数量或同时提交推断并发。早期样本不足以支持P95时记样本不足，最终性能阶段按约定补样本，不捏造分位数或前期无限补测。

交付完整源码/构建和启动方法、真实入口、采用版本、各必需组件状态、数值/功能/性能结果及未完成项。200/280 tok/s等挑战值若未达到，继续处理有证据的剩余瓶颈或如实交付阶段成果；不能把物理上限当可证明的停工条件，也不能宣称目标已达成。
