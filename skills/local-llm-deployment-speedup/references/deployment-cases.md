## 案例一：四卡 V100

这条路线由作者先使用**ChatGPT定时调研**发现1cat更新与新草稿，再使用**Codex实施适配、优化和实机验证**。调研提供候选与方向，最终效果来自代码修改、真实部署和同条件测量。

2026-11-11短Python测试中，**4卡V100共同运行一个27B请求，首轮解码速度峰值约522 tok/s，后续整轮补测约523 tok/s**。两次测试分别记录；均是单请求完整解码阶段的速度，不是并发总吞吐或流式包瞬时峰值。

### 配置与实现路线

- 硬件：4×V100 SXM2 16GB，TP4。
- 主模型：Qwen3.8-27B-pi-NVFP4，沿用原始NVFP4权重。
- 底座：1Cat-vLLM 1.5.2，在该部署上做局部适配与优化。
- 草稿：从原DFlash2转向DSpine；转换为适配SM70的NVFP4实现，接入现有投机验证链，最终保留K7。
- 后续继续修复生成内容的前缀续接与缓存回收；522读数来自这些工作之后的正式服务短测。

参考项目为[1Cat-vLLM](https://github.com/1CatAI/1Cat-vLLM)和[DSpine](https://github.com/Tencent/DSpine)，草稿权重为[Qwen3.8-27B-DSpine-b16](https://huggingface.co/tencent/Qwen3.8-27B-DSpine-b16)。本例记录本机移植结果，不将其写成上游开箱成绩。

**最终草稿是DSpine K7 NVFP4。** 运行架构为`DFlashDSpineDraftModel`，实际加载DSpine权重；配置中的`method=dflash`是复用的后端入口名称，不代表仍使用旧DFlash2草稿。AI识别模型时应同时核对权重、架构和实际加载分支，不只读一个method字段。

### 1. 保留独立尺度，融合Pi投影

Pi的GDN输入投影有独立校准尺度，不能为合并算子而统一缩放。原路径分多次NVFP4计算再拼接；优化后合成一次投影，同时保留FP4码、E4M3块尺度和逐输出通道的FP32全局尺度，由内核按通道读取。

在相同8K输入、2048输出预算、温度0.6的对照中，单路采样解码窗口速度**104.32→121.35 tok/s**。四卡真实跟踪确认新投影实际执行；该阶段属于执行成本优化，不依靠更换草稿提高接受率。

可复用方法：先核对模型的尺度语义，再融合计算；不能把权重容器同名当成数学布局相同。源码有补丁之后还要确认服务加载的实际模块与分派。

### 2. 把新草稿接通，并修复它增加的成本

DSpine接入涉及锚点token、桥接、codebook词表分片与TP4聚合；主要线性权重用现有SM70 NVFP4路线，FC、桥接和归一化保留FP16，条件修正分数用FP32。

草稿使用8192-token因果滑窗。初版虽然只读窗口内数据，却按长上下文分配注意力分区，产生额外成本。通过页表重定位到有效窗口，单路复用scalar路径，多路复用批量路径，减少无效分区，保留全部有效数据。

相同8K输入条件下，单路速度**121.35→141.21 tok/s**，但完整轮时**14.04→15.77ms**。这是草稿横向选择：每轮有效提交更多，抵消了新增计算；不能把这组收益写成轮时降低。

新滑窗也增加缓存占用。初版长会话切换后淘汰了一路前缀，续接约40秒；按完整资源预算每卡增加256MiB KV后，原问题请求约1.38秒，四路历史验收最低前缀命中率99.9766%。这属于当时的多路容量与缓存测试，和下面522单请求测试分开。

### 3. K变了，还要查实际形状是否走快路径

用户指定代码任务后比较K。K8起初比K7明显慢，原因包含九行形状没有进入若干专用计算、归约和Graph路径。Codex补齐了主模型/草稿量化分派、九行拒绝采样Graph、AllReduce＋RMSNorm、注意力、普通归约及GDN投影/递推。

同一387-token输入、1024-token输出、温度0.6、关闭思考的单请求任务：

| 配置 | 输出中段稳态速度 | 完整轮时 |
|---|---:|---:|
| 原始K8 | 平均235.77 tok/s | 约29.95ms |
| 优化后K8，干净进程四次 | 平均452.69 tok/s | 15.70～15.75ms |
| 同条件复核K7 | 平均469.63 tok/s | — |

K8提高约92%，最终仍保留更快的**K7**；有效K8补丁作为候选保留。不能把“做过K8优化”写成“522来自K8”，也不能将这里的中段稳态值与下一节的完整解码均速算成同条件收益。

轨迹还揭示每轮九字节的阻塞回传：数据很小，等待很大。接入Graph后，16轮中的该回传从16次降为0。优化依据是同步与关键路径，而非仅看传输字节数。

### 4. 生成后续接：检查所有缓存组的共同有效边界

一次长生成后，前端已经完整保留原始token，下一轮仍重算了大段正文。逐组检查发现：FullAttention和GDN/Mamba状态仍在，但滑动窗口块被优先覆盖，导致整个Hybrid前缀回退。

修复回收顺序，同时保护原输入重发和最近生成检查点所需窗口；仍允许普通LRU回收，不扩大缓存池。相同80911-token续接输入，命中**68224→79872**，服务端TTFT **4846.828→539.047ms**；前轮12526和续接128个输出token与修复前逐项一致。

共同恢复边界、回收保护和合法尾算的通用排查见[缓存故障处理](cache-failure-cases.md)；长思考模型按[专项步骤](reasoning-prefix-cache.md)继续核对。

这说明“prompt重复命中”不能代替“实际生成后的续接”。定位时按各缓存组查缺口，也不能只查模板或只扩大容量。此处是独立的长缓存修复结果，不把它纳入522短请求的测速时间。

### 5. 温度0、关闭思考：单请求峰值约522 tok/s

2026-11-11在正式服务上顺序运行短Python请求，未修改正式配置或重启。请求温度0，`reasoning_effort=none`、`enable_thinking=false`，输出上限384 token，均自然结束，实际思考输出为0。

| 单请求任务 | 输入token | 实际输出token | 服务端完整解码速度 | 服务端TTFT |
|---|---:|---:|---:|---:|
| LRU缓存 | 117 | 246 | **521.630 tok/s** | 244.543ms |
| 区间合并 | 111 | 261 | 470.353 tok/s | 455.783ms |
| 滑动平均与clamp | 112 | 253 | 507.539 tok/s | 457.217ms |

解码阶段排除首token：LRU记录为**245 token / 0.469681883秒 = 521.630 tok/s**，取整约522。服务端指标前后完成请求计数只增加1；四卡为同一请求协同计算。

包含首响应和网络等待的整次请求速度约254～335 tok/s。该轮尝试同时提交四个请求时实际串行，不能把它当四路并发峰值。生成代码去除围栏后AST语法检查通过，本轮没有执行生成函数，不宣称其运行正确性已验收。

### 6. 与整轮截图对齐：13.57～13.77ms/轮

随后独立运行相同三道短题，额外采集实际投机轮数。温度0、关闭思考，仍为DSpine K7、单请求。截图对应下表，不把这轮523.126写成上一轮521.630的同一次测量。

| 任务 | 平均整轮耗时 | 实际产出/轮 | 吞吐 |
|---|---:|---:|---:|
| LRU缓存 | **13.77ms** | **7.21 token** | **523 token/s** |
| 区间合并 | **13.65ms** | **6.50 token** | **476 token/s** |
| 滑动平均与clamp | **13.57ms** | **7.00 token** | **516 token/s** |

原始计算量分别为：

- LRU：246个输出、34轮、468.338389881ms解码；折算13.774658526ms/轮、7.205882353个有效token/轮、523.126024459 tok/s。
- 区间合并：261个输出、40轮、545.945539139ms解码；折算13.648638478ms/轮、6.5个有效token/轮、476.237978627 tok/s。
- 滑动平均：253个输出、36轮、488.687776029ms解码；折算13.574660445ms/轮、7个有效token/轮、515.666673817 tok/s。

口径为`服务端decode时间增量 / 实际推测轮数`，包括该解码阶段内草稿、验证、采样和等待的总体成本，排除prefill/TTFT；这是阶段平均折算，不是单算子计时或逐轮GPU事件。实际产出用`(完成输出token−首token) / 实际轮数`，不把K7当成每轮固定输出7或8个token。自然停止可能截掉最后验证批次多余token，按实际交付量计算。

AI复现或比较时，成组保留同次请求的轮时、产出和速度，使用未舍入值计算；不能拿截图舍入值反推更多精度，也不能混用前后两次请求的数据。

### 如何复用这条路径

**定时调研发现候选 → 核对目标硬件与现有源码 → Codex完成适配和执行成本优化 → 比较真实任务 → 检查缓存与质量 → 保留实际更快的组合。**

定时调研不自动改生产配置；发现新草稿不等于换上就快。草稿切换、实现优化、K选择和任务设置各自记录，避免把不同条件的数字连成一条百分比曲线。完整流程仍按[主入口](../SKILL.md)，本例的历史长测规模和具体参数不是默认测试规模。

## 案例二：双 2080 Ti

双2080Ti上的这条路线，先把IQ3_XXS的专家供给和执行通路做好，再在IQ3_S上继续优化内存、双卡分工与状态管理，最后将成果带回IQ3_XXS。优化逐步积累，形成了可复用的SM75部署方案。

以Python单项完整轮次ms作为主指标。**后期Python测试采用温度0、关闭思考：常态约21～22ms/轮，短时最低约18ms/轮，吞吐峰值220+ tok/s。**

本篇展示各阶段数值；具体怎样改见[工程拆解](optimization-engineering.md)，包含专家供给配套、SM75形状适配、双卡交接、状态轮换、前缀提交与跨模型继承。实际测速可复用[Python原题](../assets/python-round-baseline.md)。

### 1. IQ3_XXS：从可运行到22ms级

起始配置为双RTX 2080 Ti 22GiB、NVLink、96GB RAM，Strata / SM75、MTP4，完整专家、262144上下文容量、INT8 KV分层和视觉能力。

首次HTML功能请求为**52.58ms/轮、57.6 tok/s**。当时重复惩罚使双窗口退回串行，专家命中83.0%，CPU专家累计项25.83ms/轮。首先处理实际执行分支，再解决专家供给。

下面按Python单项列出后续优化过程。此阶段使用883-token的CSV汇总任务、温度0.6、关闭思考；后期切换为温度0的短Python测试。

| 优化步骤 | Python轮时 | Decode | 怎么达到 |
|---|---:|---:|---|
| MTP放到首卡 | **37.52ms** | 92.0 tok/s | 调整草稿位置，减少发起开销和双卡资源冲突；配套解决惩罚请求的流水线路径 |
| 专家缓存适配 | **25.81ms** | 132.9 tok/s | 让热点专家及时驻留显存，Python专家命中升至99.0%，大幅减少CPU专家供给负担 |
| 草稿投影打包、显存预算整理 | **26.27 → 25.60ms** | 126.9 → 131.7 tok/s | 对四块真实Q8草稿投影无损预打包，协调专家缓存、草稿、KV和工作区 |
| SM75 mode8专家布局 | **23.28ms** | 142.4 tok/s | 按真实混合IQ/K格式、矩阵尺寸和路由形状选择更合适的专家计算布局 |
| Q5_K草稿输出头适配 | **22.88ms** | 149.0 tok/s | 针对单token输出头优化warp分工，保持原归约顺序和词表，减少草稿链开销 |
| 精确注意力、及时交接 | **22.95ms** | 146.6 tok/s | 前段完成后立即入队后段，优化注意力chunk和merge，减少双卡等待 |
| 独立投影分支 | **22.24ms** | 154.4 tok/s | 将仅依赖本层输入的门控、查询等投影放入已有并行分支，增加计算重叠 |

这一阶段的大收益来自**专家缓存与CPU供给**，之后才是SM75专家计算、草稿输出头和双卡重叠。逐步记录也保留了小幅波动，例如22.88→22.95ms；优化看整体执行效果。

### 2. IQ3_S：继承底座，继续减少供给与状态成本

IQ3_S继承上述SM75、流水线、注意力、提交/回滚和前缀实现，适配原生Q4 MTP与自身专家布局，然后继续优化。

| 优化步骤 | Python结果 | 怎么达到 |
|---|---|---|
| 专家供给组合 | **28.88 → 25.45ms/轮** | 大页内存布局、交换缓冲轮换和更及时的驻留适配一起实施；专家命中91.2%→96.0%，CPU累计项13.47→7.80ms/轮 |
| 双卡工作重新分配 | **168.74 → 170.43 tok/s** | 使用温度0、关闭思考的382-token Python 12函数任务；层分工由24/24调整为22/26，将草稿占用一起计入GPU负载 |
| GDN快照轮换 | **21.1174 → 20.8037ms/轮** | 用缓冲轮换减少逐轮状态复制；暖态两次20.81、20.80ms，对应171.0、169.5 tok/s |

这里延续的是同一套工程思路：**减少专家供给等待 → 配平主模型与草稿 → 消除重复状态复制**。IQ3_S使用自身量化和草稿配置建立阶段基线，再把验证有效的实现向后复用。

整条继承路径还包含HC prefill、MMQ驻留专家直接读取和检查点缓冲预分配，用于改善输入处理与续接；早期IQ3_XXS的终止窗口提交修复，使一次100K续问从重读约1391个正文token变成只处理33个新增token，这项修复继续被后续部署沿用。

### 3. IQ3_XXS：复用完整优化组合

将IQ3_S阶段继续完善的供给、调度和状态管理成果带回IQ3_XXS，形成完整组合：

**专家缓存适配＋内存供给与交换轮换＋SM75专家布局＋草稿投影与输出头＋双卡分工和流水线重叠＋GDN快照轮换。**

后期Python测试条件为**温度0、关闭思考**，结果为：

| 指标 | 结果 |
|---|---:|
| 常态完整轮时 | **21～22ms/轮** |
| 短时最低轮时 | **约18ms/轮** |
| 吞吐峰值 | **220+ tok/s** |

这条路线从早期约50ms的功能部署起步，Python由37.52ms逐步进入22ms级，再通过IQ3_S阶段的继续优化与回迁，达到上述后期表现。常态轮时、短时最低轮时和吞吐峰值分别列示。

### 4. 可以复用的方法

1. **先确认完整通路。** 核对主模型、草稿、惩罚、Graph和流水线实际生效，找到导致串行或重复执行的分支。
2. **先解决供给大头。** 联合检查专家命中、CPU工作、内存布局、传输和等待，共同分配专家缓存、KV、草稿与工作区。
3. **再匹配实际算子。** 根据权重格式、矩阵形状和硬件特性选择布局，优化草稿投影、输出头及独立计算分支。
4. **继续减少整轮浪费。** 配平双卡工作，及时交接，减少重复复制和状态维护，让计算与传输充分重叠。
5. **跨模型积累成果。** 保留有效实现，适配新模型的专家和草稿布局，再把成熟组合带回原模型。

Python建立基础轮时后，接着检查长上下文、前缀续接和操作者真实任务；完整阶段顺序见[主流程](../SKILL.md)。
