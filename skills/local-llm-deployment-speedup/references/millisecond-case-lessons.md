# 毫秒优化：从实测补齐隐蔽成本与实施细节

配合[阶段4主章](millisecond-optimization.md)，按症状读取对应节，不把每节变成每次必跑的实验。下面是截至2026-11-11核对的历史源码/验收和部分原始数据；未重新运行模型，原始私有记录不随技能公开。历史规模、参数及正式A/B仅说明证据，不改变主流程的短→长顺序，也不要求每个候选重做整套对照。

## 1. 请求选项会改变执行图：采样、惩罚与语法也要查

不能只冻结温度和K。沿真实入口核对默认/显式的presence或repetition penalty、logits processor、结构化输出/grammar、工具格式、验证采样方式；应用可能自动添加这些字段。查这些选项是否触发CPU掩码构造、草稿回传、逐位置串行验证、无Graph或单窗口回退。配置“支持投机”不证明这次请求走了完整快路径。

**实证：**IQ3早期52.58ms请求因惩罚选项走串行；解决对应分支才获得双窗口收益。另一次Pi诊断中，同一7552-token输入、1024输出、同文本SHA、同270轮及接受率：无grammar 240.72 tok/s，英文grammar 170.13，允许任意字符的grammar 168.35；无约束与英文约束的每轮平均为15.74/22.27ms。任意字符也慢，说明应查通用结构化执行路径，不能归因为英文难猜或接受率下降。没有函数级计时，不把6.53ms总差直接写成mask kernel耗时。

**行动：**保留用户要求的采样、格式和语言能力，修复相应执行分支。为定位做的关闭选项对照必须标为诊断，不以永久关闭必需grammar/惩罚冒充等功能提速；应用无需求却自动附加约束时，可在授权内移除该额外机制。恢复真实设置后核对快路径及所需输出/工具行为。

证据：IQ3工程拆解；`current-speed-audit/RESULT.txt`与`grammar-comparison.json`。

## 2. 主机公共准备与CPU运行状态：先分清重复、依赖和等待

按rank/worker和阶段看主机时间线。慢rank是身份、工作分配还是CPU状态导致，需要证据；某rank的collective API时间长，可能是在等另一rank到达，不直接证明互联带宽不足。检查当时CPU调频/调度、GPU时钟/温度/功耗、队列及其他负载，条件变化单列，不能把系统状态收益记作kernel改动。只读诊断不切governor、不绑核或改全机配置。

**双2080Ti 27B的三步：**

- 多个GDN group共享当轮相同的分类、mask、layout和索引准备；group专属accepted filtering、状态查询、metadata回写与KV/state更新各自保留。这是每轮共用，不是跨轮缓存全部metadata。
- rank/core交叉后，慢主要跟rank0身份走；历史改为performance governor后改善，不是靠改affinity或GPU超频。该状态不等于永久启动配置，现场需重新核对；历史阶段约数不能拼成严格单项百分比。
- 将下一轮可提前的准备放入已有GPU执行窗口，用scheduler已有准确CPU长度解除同链回读依赖；只保留一个待消费/丢弃的预备项。合并909轮/rank的Host中位32.686→30.103ms。Prepare约少3.05ms，Post-draft约多0.42ms，净兑现约2.58ms，不能把全部准备耗时都称为收益。

**实施边界：**将“可提前的公共数据”和“必须晚绑定的实际accepted数、页映射、状态位置”分开；缓存恢复、Prefix Align、批次/块映射变化、EOS和取消后，重建或丢弃不再匹配的预备项。不能直接删除guard来硬开旧快路径。复验相应边界的提交和后续续接；已有短基准足以定位时不扩成长压力测试。

证据：`2080Ti-Frankenstein_从39ms到28ms_优化全历程总结.md`第4—5节；机制与状态边界另见[27B案例](case-dual-2080ti-27b.md)。

## 3. 几字节回传也能阻塞整轮：查谁在等结果

对小DtoH和host标量读取，沿“GPU生产者 → 复制/隐式同步 → CPU分支 → 下一次提交”找依赖。字节很少不能排除大等待；API叫Async也不能只凭名字认定主机不阻塞。区分发起调用耗时、设备传输耗时及前置工作等待，不重复相加。

**实证：**DSpine K8九行拒绝采样接入Graph后，16轮中的九字节DtoH从16次到0；同窗口`cudaMemcpyAsync`主机累计188.657734→4.465737ms。72字节和4字节回传仍各16次，不能说“消除了全部DtoH”，也不能将CPU累计差直接当每轮净收益。29.95→15.70–15.75ms是多项K8修复组合的完整轮结果，不单归给九字节。

**可选改法：**已有准确host值可复用时消除无谓回读；否则将可留在设备的判定接入现有GPU/Graph路径，或延迟读取到真正消费时刻。值随接受、取消和缓存恢复改变时必须保持更新与所有权，不用旧长度或固定结果替代动态判定。验证改动后的控制分支和真实回传次数，再看正常完整轮时。

证据：`dspine-k8-opt/final-copy-audit.json`、`k8-optimization.patch`和`RESULTS.txt`。

## 4. 实际shape覆盖与调用次数：单核很快也可能没接通

在当前固定配置下列出主要真实调用：Target、Draft、输出头、采样、归约、GDN、Attention各自的M/N/K、权重/scale与激活dtype、stride、TP分片、页/工作区约束、次数及当前分派。注意主模型验证批次、草稿步和末轮截短可能产生不同形状；按现场实现核对，不一律假设是K+1。

**实证：**DSpine的K8产生九行路径，量化、注意力、采样Graph、普通及融合归约、GDN投影/递推都有覆盖缺口。最终补齐多条路线后K8接近翻倍，仍慢于同题K7，因此保留K7。该经验用于已选择配置的实现排查，不授权阶段4扫K。早期还曾误改工作台副本，实际trace没有新核；之后修改真正加载模块才生效。

**SM75矩阵例：**27B的五种实际投影分别选择tile/blocks，按真实调用次数加权的Graph微测14.233421→13.589865ms，服务28.894/29.679/28.902ms回切对照支持约0.777ms改善。不同矩阵不能机械统一tile、提高blocks/SM或occupancy；workspace容量和稳定地址须与选择一起匹配，未匹配形状保留原路径。这里的M=8与各blocks数不是其他机器的默认值。

先用真实权重和生产函数做必要局部筛选，按实际次数与重叠位置估计影响，再接入真实运行器。记录期望/实际调用数量、加载库身份和分派证据；只验证环境变量、源码存在或一个Graph捕获日志不够。不同设备、批次、末轮和不匹配条件只补受影响的回退检查，不做无界shape穷举。

证据：`dspine-k8-opt/RESULTS.txt`、`candidate-final-trace-summary.json`；双2080Ti总结第5节；[V100案例](case-v100-pi-dspine.md)。

除快路径是否命中，还要核对有效行数与补齐后的图尺寸，Graph之外的plan/JIT/capture是否重复发生，以及eager/分段图转入完整图时的旧异步工作是否仍在读写静态缓冲。相关公开代码见[仓库对照示例](github-runtime-comparison.md#本轮公开源码核对示例)；这是代码层面的补充检查方向，不是新增本机实测收益。

## 5. 融合前先找重复数据准备，并保留数值语义

查同一输入是否被相邻Q/K/G或Gate/Up各自转换、重排、归一化或gather；是否能将准备移出矩阵内循环、让消费者直接读取已准备布局。确认权重码、块尺度、逐通道/分片全局尺度、中间舍入点、累加顺序和输出dtype，不能因统称NVFP4就合并尺度，也不能默默消掉原来的BF16/FP16舍入。

**Pi GDN：**将多个投影与拼接融合，同时保留FP4码、E4M3块尺度、逐输出通道FP32全局尺度及既有尺度舍入顺序。目标M8投影58.01→22.63µs，四卡每卡16步trace的总调用数24420→21920；整模型同8K条件单路104.32→121.35 tok/s。三个量分别是局部耗时、调用数量和请求表现，不能混算收益。36项实际权重检查中28项decode逐位一致，8项prefill有舍入差异但FP64抽样误差未退化；这不是所有输入逐位等价的证明。

**Ripple65B：**先把激活重排移出内循环并共用转换结果；后续将RMSNorm＋blend＋输入准备、残差＋归一化＋准备、gate/SwiGLU＋准备局部融合，矩阵核直接消费已转换输入，保持BF16中间舍入和原累加顺序。固定22输入/17输出、一轮接受15/15的特殊短样本，完整轮41.076→39.529ms；不能用这一个满接受微样本声称通用业务吞吐或质量。进一步跨卡求和融合实测反而慢，撤回；“融合更多”不是目标。

对改变的算子用真实权重、实际T/分片和相关边界做数值/状态对照；可精确保持的检查逐位一致，确有合法浮点差异时按约定误差与参考计算验证，不能只看最终一句话相同。局部正确后仍验证完整路径和受影响的续接；不要求每次改动重新跑历史全容量测试。

证据：`pi-opt/ACCEPTANCE.md`、`delivery/numerical.json`；`ripple65b-ninfer-20261106/DELIVERY.md`、`fusion-kernel-tests.json`。

## 6. 旁流、跨卡事件和缓冲复用：并行要落实到消费者

沿生产者写完、消费者读完、缓冲可复用三个时刻核对事件与所有权。区分GPU仍未完成、已经完成但主机没有及时提交下一段、两条分支竞争同一GPU资源。满足前提才做旁流与事件替换，不以删除同步追速度；一个稳定指针也可能指向被下一轮覆盖的内容。

**Ripple实例：**交替使用注意力和FF两个归约源缓冲，由下一次来源就绪屏障保护旧缓冲复用，去掉重复即时消费屏障；与激活重排及窄K/V矩阵改动一起，将42.727→41.076ms，不能把组合收益全归给屏障。权重上传与重排沿同一stream排序，修正过加载顺序错误；启动成功不证明异步加载依赖正确。

**IQ3实例已在[工程拆解](optimization-engineering.md)展开：**两卡分工把草稿占用算进去，前段完成就提交后段；仅依赖输入的投影可放独立分支；GDN通过状态版本ring减少复制而保留回滚。后期就绪到下一窗口启动仅约0.15ms，提前轮询无收益，不能继续把主机轮询当最大瓶颈。

改动后查实际提交/拒绝、末轮EOS/length、取消及相关续接，按实现选择边界即可。若减少快照写入却增加第二遍递推，计完整层数、全部必要提交和资源竞争，不能只报record-only成本降低。线程/stream增多或图内时间缩短都不自动代表完整轮更快。

证据：Ripple交付第二—四阶段；IQ3工程拆解第5—7节及[27B状态边界](case-dual-2080ti-27b.md)。

## 7. 低扰动测量不止“关掉profiler”：查进程残留与未覆盖路径

先用原生请求统计和少量同流事件定位区段；需要更细归因才采短trace。每rank保留可关联的阶段顺序、实际调用次数和窗口，不能直接相减不同GPU事件；先确认埋点函数真的被异步运行器调用。图内kernel累计、完整事件跨度、主机整轮与请求摊销分别解释，早段/后段及首尾排空也分开。

**历史反例：**

- DSpine K8在Torch profiler之后，同进程普通复测约422 tok/s；同配置干净进程恢复450–456。诊断进程状态影响需单列，未证实具体驱动根因。不能仅因退出profiler就把后续读数视为无扰动。
- Ripple插入GPU事件后完整轮约42.91ms，正常约39.55ms。`verify-phases-summary.json`中MLP投影约15.725ms、约占所测分段GPU时间45%，可用于找热点，不作为正常轮时或可直接兑现的节省。
- Bonsai早期trace写出卡住、一次导入器报`Wrong event order`；保留有效早期段，但不用失败请求的吞吐作基线，也不使用无法信任的时序。相同请求输出越长后段attention成本越高，不先归因为草稿接受率下降。

关闭诊断后若读数异常，先核对进程、设置、负载与冷热条件。在已授权窗口中才用干净实验进程复核；不能为测速擅自重启共享服务。重载会丢热KV，重新建立同条件预热/复用样本，不能把重启后的冷请求与原热请求直接相减；没有条件恢复可比测量时标证据受限，不强行给收益。

证据：`dspine-k8-opt/RESULTS.txt`；Ripple交付第五阶段和`verify-phases-summary.json`；`Bonsai_DFlash2_Graph_AB_2026-09-25.md`。

## 8. 局部正确或更快之后，如何决定继续、保留或撤回

用“实际覆盖多少调用、占关键路径多少、是否转移成本”解释候选价值。先用少量真实形状/权重筛掉明显退化，再做必要整合反馈；微测不胜且无其他必要收益时，不为凑流程进入停服长任务。前期不要求每个小改正式ABBA，正式比较仍在阶段8。

**负向证据：**mode8 T1/T2候选两卡各1232次数值对照逐位一致，但主格式gate/up慢约4.9%–11.4%，未进入真实任务A/B。Q6草稿头微测473→413µs，真实Canvas/Three.js等ABBA未证明净收益；部分长输出在原版重复运行间也不同，不能将吞吐差都归给kernel。HTML样本只有75 token的等待工具调用，不能称HTML视频长代码生成已验收。

**候选可以有条件重新评估：**双2080Ti Draft Attention曾被Prepare增长抵消，跨轮准备/align依赖改善后才重新验证并获得30.311/29.410/30.314ms对照支持。重新尝试要写明改变了哪个依赖或假设，不能永远封杀旧候选，也不能原样反复扫参数。

收尾至少能说明实际保留的源码/二进制/配置、受影响功能与续接、正常完整轮读数、剩余最大成本及下一步。返回健康不证明候选已卸载，恢复源码不证明进程已回退；核对实际产物。没有收益可以结束该候选，但在授权目标尚有可推进方向时继续，不把所有失败都交回用户选择。

证据：`mode8-narrow-20261102/RESULT.txt`；`pipeline-candidates-20261102/e2e/RESULT.txt`；双2080Ti总结第5节。
