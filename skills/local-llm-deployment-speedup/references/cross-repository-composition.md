# 跨仓库组合：按瓶颈借部件，接成完整运行路径

**缝合是Frankenstein的核心方法。** Strata＋1Cat＋Basalt＋Radiance这样的组合，表达的是从不同仓库吸收适用部件并形成完整运行路径；具体职责与版本以实际采用代码为准，不按名字预设分工。

默认顺序是：**找到快的部位 → 查清为什么快 → 拉取相关源码 → 设计目标硬件上的等效实现 → 缝合并验证。** 可直接复用的代码优先复用；不支持V100等目标设备时，拆开可迁移的算法/布局/调度机制与硬件专用实现，按需要改写后者。减少的是无依据的重复研发，不是限制适配代码量：为复现已明确的收益机制，必要的kernel、wrapper、分派和状态配套应完整写好。有明确来源就直接推进，不为证明“没有别的实现”做无限调研。

这套方法的重要经验是：**每个仓库取适合的一部分，在目标硬件与模型上组成有效部署。** 整仓库TPS用于最终对标，不能代替部件选型。即使某引擎在某次V100测试中较慢，它的调度或缓存仍可能有价值；另一个引擎为别的模型写的高速内核，也可能适配当前矩阵。不能把历史条件下的快慢写成某仓库的永久属性。

需要寻找来源时读[GitHub源码对照](github-runtime-comparison.md)；下面解决找到候选以后怎样拼接，以及历史案例实际证明了什么。

## 三种不同的融合

| 类型 | 实际动作 | 应说明的边界 |
|---|---|---|
| 组件移植/组合 | 当前运行器接入其他仓库的kernel、collective、视觉模块或状态实现 | 来源代码、宿主调用位置、接口转换与共同资源 |
| 机制借鉴与改写 | 借用预打包、分块归约、共享读取、流水线等思想，针对本机指令和shape重写 | 哪部分思想复用、哪部分实现不同，不能称原内核直接移植 |
| 算子融合 | 合并投影、归一化、量化或中间准备，减少launch、重复读取和中间存储 | 数学运算、尺度、舍入与状态语义是否保持；可与前两类一起发生 |

“融合了某仓库”必须落到具体部件。不能用一处算子融合代替跨仓库方法，也不能把机制相似写成代码来源已证实。

## 先确定宿主和来源部件

以真实瓶颈作为搜索单位：通信等待找collective，量化投影慢找适用的解码/矩阵内核，图片处理慢找视觉计算，续接重算找token与状态管理。保留已有有效服务、草稿和缓存路径，从来源仓库吸收所需能力。若完整换底座确实更合适，按用户范围评估完整迁移成本，不把保留当前引擎变成禁令。

来源可以跨模型、精度和显卡，但迁移判断必须落到局部运算：模型名称不同不等于不可用；都是MoE也不等于格式兼容。先看输入/输出维度、批量行数、路由、量化码与scale、注意力与状态结构。其他模型大批量快的GEMM不一定适合本机T=1或投机T=K+1；SM70的指令实现也不能原样拿到SM75。保留机制，必要时改写实现。

在原部署记录写一行就能开始，不要求新schema：

> 宿主及保留部分 → 当前瓶颈/耗时 → 来源仓库与固定commit、文件/函数 → 直接移植或机制适配 → 要接通的依赖 → 预期省去的工作与验证方式。

来源版本暂时缺失时注明未锁定，先定位可读取代码；不能凭记忆伪造commit，也不为记录格式阻塞独立工作。公开引用和正式保留改动时记录实际采用版本、许可证与署名。

## 找到快的原因，再决定如何移植

这一过程是常规缝合主线，不必等到现成组件全部接失败后才启动。目标是形成一条可实施的因果链：**外部哪个区段快 → 少做了什么或怎样提高利用率 → 对应源码 → 本机也有哪项成本 → 目标设备怎样实现 → 怎样证实节省。**

### 1. 把“项目很快”缩到具体路径

从可比任务、benchmark和profile定位是prefill、decode、专家供给、通信、注意力、状态还是请求处理更快。记录实际硬件、精度、shape、冷热和计时边界。小模型、更低精度、缓存命中或不同输出轨迹造成的差异不能直接当实现优势；没有可比测量时先写“源码支持的收益假设”，不要把仓库宣传值当根因。

沿入口、准备、分派、kernel与消费者读完整相关链，并回答以下具体问题之一：

| 可能的速度来源 | 源码中要找到什么 | 本机迁移要保住什么 |
|---|---|---|
| 少读/少搬数据 | 打包布局、驻留、共享读取、直接指针，原来多出的复制或解码 | 实际字节量、复用次数与数据生命周期；避免桥接又复制一遍 |
| 少算/少启动 | 公共准备复用、投影/归约融合、窄shape专用路径 | 运算、scale和舍入语义，以及每轮调用次数 |
| 更高并行度/利用率 | tile、split、线程/warp映射、归约、向量读取 | 目标SM资源、实际M/N/K、尾部与工作区；不是照搬tile常量 |
| 隐藏等待 | 供给流水线、预取、异步通信、及时发布与消费 | 真实依赖、重叠区间、暴露等待和缓冲所有权 |
| 避免重复处理 | 模板/metadata复用、KV/Hybrid状态与图片特征缓存 | 真实身份、生成续接、提交与恢复边界 |

优先利用已有测量、相关补丁前后记录及测试。需要消除关键疑点时补一个针对性的局部测量或路径对照，不把找原因扩成每步正式A/B。有多项共同变化时，区分确认的机制、推断的贡献和待测收益，不强行给每项分摊ms。

### 2. 拉取能支持实现的源码

候选确定后取得相关仓库/fork的本地源码，锁定commit，沿用已有checkout或隔离工作目录；按相关文件、调用者、构建依赖和测试读到足以修改的深度。需要编译的依赖再取对应版本，不只看README/单个函数，也不为一个部件无条件下载全部权重和无关仓库。已有镜像或源码足够时继续工程，不重复拉取来凑流程。

读清来源实现的输入输出、权重表示、准备阶段、工作区、启动条件及回退；与宿主已有接口对齐。采用的是源代码、量化格式、数据布局还是算法思想，要分别记录。不能因某引擎没有整个目标模型的支持，就跳过其中可用的算子或调度机制。

### 3. 没有V100支持时，写出机制到SM70的映射

将来源拆成三层：**运算/数据语义 → 获得速度的机制 → 特定硬件指令与调度。** 前两层可能可迁移，第三层按目标工具链、实际指令能力、共享内存/寄存器和互联重新实现。先查已采用仓库中适合SM70的对应实现作为落点；找不到可直接接入的版本，再编写所需设备路径。不能仅修改架构检查或删编译guard就称已移植。

在原工程说明中列出实际要改的文件/函数即可，例如：

> 来源kernel/调用者的快因 → 可保留的布局/算法 → 目标不支持的指令或资源假设 → SM70替代路径 → 新wrapper/分派/工作区 → 实际shape数值检查 → 计时与整合入口。

若来源收益依赖目标设备没有的专用能力，评估能否保留减少读写、准备复用或重叠等待等机制。软件兼容路径可能更慢，不能宣称速度等价；有依据的替代实现继续完成，确实失去收益基础才舍弃该候选。不要把“原生不支持”直接裁成“无法借鉴”，也不要为凑仓库组合强留无收益路径。

### 4. 把实现计划写到能动手编码

说明宿主的哪个入口调用新路径，来源哪些函数直接复用，哪些需改写；给出输入/输出、布局与尺度、设备/shape分派、workspace分配与回收、stream/event和Graph接入。必要时先写代表性shape的参考与单算子入口，确认数学/格式语义后接入调用者；保留其他shape的正常路径。开发顺序按依赖，先形成可运行的必要组合，之后针对剩余瓶颈迭代。

例如本地Strata/Basalt接入记录把IQ内核落实到 `iq_mmvq`、`iq_dequant_f32`、专家调用者与MMQ工作区；Radiance格式记录则给出编码定义、plane、码本、scale和旋转参考作为CUDA适配依据。这些是“如何写”的入口：沿已知表示和函数边界移植。格式已读懂、单对象已编译都不证明获得速度，仍需实际路径、数值与完整请求验证。这里说明方法，不为Strata＋1Cat＋Basalt＋Radiance预设固定职责或组合成绩。

## 接成最小完整组合

只核对与选中部件相关的接口和依赖，不建立大而全的兼容矩阵：

1. **表示边界。** dtype、量化码、scale/zero-point、矩阵布局、stride、padding、分片顺序是否一致；视觉特征的顺序/尺寸/精度是否符合宿主；状态相关移植另查token、位置与KV/Hybrid提交边界。保持既定精度语义，不能暗中降精度制造收益。
2. **运行链。** 配套wrapper、metadata、构建注册、实际分派、Graph捕获、workspace、stream/event和消费者一起接通。删guard使函数被调用，不等于能力适配完成。必要的布局或预打包可以在加载期做，不应每轮重复转换。
3. **组合成本。** 查新增转换、主机往返、跨卡复制、序列化、同步和重复权重/工作区。两个独立引擎各加载一份模型可能吃掉KV或专家空间；可行时以模块接口共用数据，并去掉已被替代的重复组件。
4. **实际采用。** 用已加载产物、分派或trace证明宿主调用了新组件；检查代表性的实际shape和其他shape正常回退。只编译通过或源码有该函数，不算接入生效。

先完成能运行的必要依赖包，再做局部数值/状态验证、短完整请求计时及受影响缓存/功能检查。若第一包慢且缺已知依赖，补齐后再裁决；依赖已完整、成本已解释仍无收益，则保留证据并撤回。不要对每个开关穷举正式A/B。长测试和最终对标仍按[主流程](../SKILL.md)及用户范围安排。

## 历史案例与可迁移经验

以下来自作者本地源码快照和验收记录，原始运行日志未随技能公开。它们解释选择和接法，不声称当前服务仍运行这些版本，也不是本轮新基准。使用时重新锁定目标源码。

### NInfer语言运行器＋1Cat视觉计算

2026-10-25的保留记录中，语言侧继续使用NInfer TP4/MTP4，接入1Cat的FP16 TP4视觉计算路径：读取同目录原始BF16视觉权重，交付真实BF16图像特征。去掉NInfer重复视觉塔及其工作区，保留原图预处理、多图、历史图片与精确特征缓存。这里是视觉子系统组合，不是图片先转成文字，也不是换整个语言引擎。

同机同六张4096×4096图片与提示词参数，视觉耗时287.930→46.979秒；完整请求330.306→90.174秒。输入均为98,399 token，但输出227/234 token、MTP54/59轮不同；约98K任务整轮15.2793/15.3303ms基本持平。因此收益明确集中于视觉，不据此宣称语言decode或所有任务都获得同倍数提速。显存峰值也提高，必须计入组合预算。

记录还验证了不重传图片的续问、历史前缀复用，以及修改文本前缀后仍复用图片特征。可迁移经验是选一个清楚的特征接口接入模块，同时处理重复驻留、图片语义和缓存。

### NInfer吸收1Cat通信与计算机制

本地NInfer `docs/performance.md`明确记录1Cat启发的大allreduce reduce-scatter/allgather与TP4 Split-D prefill；后续还组合投影发布、归约、归一化与GDN调度等优化。这说明借鉴不限于视觉模块，也能进入语言推理核心。

该记录的85K输入最终成绩包含多项连续改动，不能归给一次“接入1Cat”。Split-D改变浮点结合顺序，部分阶段输出也变化；后续保留token/计数的结论各有自己的基线。迁移时分别追通信协议、分片和数值边界，不把“受1Cat启发”全部写成原代码直接复制，也不从累计成绩推单内核收益。

### Strata借用其他实现的量化内核

本地Strata/Gyro说明 `GYRO.md`明确写出trellis prompt MMQ来自agentionai的llama.cpp fork。该版本通过 `cmake/strata_ggml_tq_overlay.cmake`、`third_party/ggml-tq/`与固定ggml配套，把三类trellis类型接到自有MMQ库；直接对该fork构建时使用其已有实例。overlay锚点不匹配会关闭该路径并回退较慢的FP16路径。

这是明确的来源部件复用：宿主沿用Strata运行机制，量化计算来自另一实现；不能只看“仍叫Strata”就认为内核全部来自Strata。也不能只复制tile loader而漏掉类型注册、构建与分派。来源模型能高速运行只是线索，当前模型是否获益取决于实际格式、shape与供给路径。

### 从V100 fast decode机制改写SM75 Q8路径

2026-10-28双2080Ti记录借鉴V100的预打包、合并读取和小批量适配思想，沿用Strata无损Q8_0预打包，新增SM75双行输出读取并共享q8_1激活；不是直接移植SM70 QPN/MMA。只对三类实际主投影、T=1..4启用，其他形状沿用已有分派。

两卡实际形状Graph数值检查逐位一致；局部T=4内核约改善17%～28%，一次整合验收前两题完整轮时31.668→31.108ms，仅约1.77%。T=1收益很小，预打包还增加约956.2MiB/卡。说明跨硬件借鉴可以成立，但需要按实际shape改写，并用完整轮与资源占用衡量价值。

### 配套齐全仍无收益：原生IQ融合候选撤回

另一条IQ3路径适配上游PR3277的原生IQ融合prefill，覆盖实际七组格式和两GPU，数值与缓存检查通过。第一包实际命中但仍用96槽环；依据消费者约束补齐512槽环后，约1K的两个冷prefill仍从1800.4/2003.2ms退化到2342.1/2360.9ms，最终恢复原供给组合。

这同时说明两件事：未接完整依赖时别急着否定来源；完整接通后也不能因“上游快、融合了、数值通过”就强留。这里仅否定该硬件、短输入和供给组合下的候选，不外推为所有模型/长度无效；decode输出与窗口构成不同，其读数不能归因给prefill内核。

## 交付时说明组合本身

写清每个实际采用部件来自哪里、宿主保留什么、改写了什么、如何编译/分派、最终计时和缓存是否通过。区分源码已纳入、实际已调用、整合后确有收益；不同阶段成绩不能拼成一个虚构的统一A/B。维护接续时同时保留来源版本和本地适配补丁，避免下一次升级覆盖已验收的组合。
