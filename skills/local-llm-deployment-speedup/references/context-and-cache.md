# 阶段5：上下文增长、两类缓存与首响应

**开始前先核对短阶段：全部主要传输与等待已查清、优化算子确实生效、短前缀续接成立。未完成就回到阶段4，不先跑长请求。** 本阶段以速度为主线，普通回答质量问题单独记录，不扩成全面模型质量评测；状态串用、错误缓存、输出损坏等执行错误仍需修复。

出现旧前缀/生成段异常重算时，按[缓存破坏专项](cache-invalidation.md)逐层定位，并参考[十二类故障处理](cache-failure-cases.md)。长思考模型另读[思考内容与KV快照专项](reasoning-prefix-cache.md)，不能只测相同prompt重放或普通短回答。细节按症状读取，不要求每次全文加载。

## 分开四种状态

1. 权重/编译/Graph是否已暖。
2. 显存专家缓存是否已填充及实际命中。
3. 请求前缀KV与Hybrid状态是否可复用。
4. 应用是否直接返回旧答案。

前两者不能证明第三项，第四项不能冒充第三项。首次没有公共前缀的冷请求不是缓存故障。即使输入前缀命中，decode仍可能随历史增长而变慢，应分别看每轮执行与新增输入处理。

## 逐步增长，按证据分解ms

沿真实模板与入口逐步增加历史；无另定规模时，本阶段可从约10k-token输入开始，分别观察冷输入、跨请求复用、带实际生成内容追加新输入。阶段4的短基准不被这个10k起点替代。

先选少量与用途相关的位置，再按目标窗口推进；不默认冷填充接近满上下文，不把短输入后生成很长称作“始终短上下文”。接近满窗口冷测仅在操作者明确需要并纳入范围时做，容量上限与常用负载分开。

每个位置记录有效上下文、完整轮次ms、注意力/状态处理、传输和等待、真实命中/新增计算，以及资源使用。固定模型/草稿/K，沿用短阶段的温度0、零思考或已约定的实际可用设置；本阶段不以接受率下降为理由开始K调优。

区分：长注意力扫描增加、状态快照/提交增加、KV回收/恢复、专家供给退化、主机处理历史开销。不同输入内容造成的专家访问或输出差异要记录，不能把所有差异归因长度。无法控制的部分保留限定，不必因此重建完整benchmark平台。

注意力扫描或归约成为主要增长项时，进入[长注意力专项](long-attention-optimization.md)：区分KV页、kernel tile与split，按硬件/shape选择实现，核对Graph与真实分派，再验证完整轮时。公开源码入口与适用条件见[实现参考](long-attention-cases.md)。

## 前缀身份与完整可恢复状态

检查真正传入runtime的token序列，包含system、工具定义、历史、reasoning、工具结果、图片位置和模板特殊token。文字相同可能因重新分词/空白处理形成不同token；保留实际生成token的实现也必须符合当前模型、模板与会话身份，不能跨模型/用户盲目复用。

重点核对模板trim/重渲染、思考段保存/返回、工具调用及结果格式、动态字段、图片顺序和processor版本。只优化可等价复用的部分，不冻结动态事实、删历史、删工具或缩短思考来刷命中率。

Hybrid模型同时核对Attention KV与GDN/SSM/卷积等状态、页映射、检查点和已提交前缀边界。全Attention KV存在不证明完整状态能恢复；允许的块边界重算如实记录，不要求所有尾token零重算。只测最终一个state tensor不足以排除中间状态问题。

状态/旁流改动用实际块/页边界附近的短样例查提交、拒绝、取消和后续复用；只有涉及这些分支才补对应测试，不把所有分支变成每次文档修改的门槛。Graph地址稳定不保证内容所有权稳定，消费者完成前不能覆盖其metadata/buffer。

## 从首次不一致位置定位续接问题

把下一请求的实际token序列与上次已提交序列对齐，找出第一个不一致位置，再查该位置对应的模板、停止条件和状态提交。若分歧就在EOS/长度结束附近，检查窗口是否多提交了尚未交付的行；若发生在图片或工具边界，则查对应模板和处理结果。

结束窗口若先提交所有行、再按EOS截短输出，会让内部状态多走，续接只能退回旧边界。将实际有效行数同时用于Target提交、consumed/live、位置和投机撤销，修复共同状态前沿，而非仅裁剪文本或扩大池。

高命中之后再查固定准备成本：预分配空白检查点存储、复用内存池、适当并行保存；每次仍写入当前真实状态。对象回收时重置请求相关计划与metadata。实施细节见[工程拆解](optimization-engineering.md)的生成结束与短续接章节。

## 专家缓存与KV的共同资源检查

混合卸载部署随着KV增长，观察专家驻留预算、实际命中、换入换出、CPU计算与传输等待。按 [毫秒优化](millisecond-optimization.md) 的真实口径统计，不将路由命中率和字节命中率混用。

测试正常长短会话交替与复用间隔，检查长请求之后短请求是否频繁重算、专家是否反复换入。静态预留与动态使用分开；一次满载无OOM不能证明切换后缓存仍可用。若专家缓存扩容挤掉前缀，或KV扩容让专家供给严重退化，应按阶段3整体预算调整，在已确认取舍内执行，实质容量变化需要讨论。

## 首token先查缓存与图片等处理

顺序为：实际复用机会和命中 → 新增/重算量 → 图片处理 → 模板/分词/复制/序列化 → 排队/进程传递 → 必要新输入计算。按现场证据取相关项，不机械把每一项都重写。

图片检查原图身份、处理参数、encoder/processor/模型版本、历史图片位置、特征缓存与KV完整图片边界。同图可复用时避免重复编码；换图或处理参数变化必须正确失效，不能复用错误图片特征。保留用户历史图片，不靠删除图片提高速度。

高命中但TTFT长时按[请求处理方法](request-path-overhead.md)看CPU张量传递、重复渲染扫描、拷贝和进程开销；低命中先找前缀差异与状态/池回收，不能先优化重算的prefill掩盖失效。无复用机会的首次冷请求记录其等待，若用户未要求冷输入专项暂不深入prefill。

分别记录engine首token、客户端第一段非空模型内容、首答案与实际UI显示；有思考时首内容可能是reasoning，不当作答案。网络首字节、角色事件、心跳、空delta不算模型内容。

## 验证范围

用多轮实际生成续接、不同后缀、长短交替，以及使用中的图片/工具路径验证。读写工具只用当前授权的临时测试目录，不触发真实业务副作用。prefill、命中和专家统计用请求/窗口增量，说明worker/rank与并发范围，避免多卡重复计数。

高命中目标应基于实际共同前缀和实现边界，不统一规定90%或100%。报告命中与查询计数、分母、实际新计算量和等待；未知不填0，分母0记不适用。共享业务流量无法隔离时说明只是窗口观测，不归因单个测试。

完成后留下上下文长度到ms的简表、前缀失效原因/修复、混合部署专家供给结论与剩余限制。质量问题另列。**后续温度、高思考、K或prefill改变后，仍需复查受影响的前缀路径，不能把本阶段一次通过当永久保证。**
