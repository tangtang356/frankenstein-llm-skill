# 方案、调研与阶段推进

阶段顺序以 [主入口](../SKILL.md) 为唯一入口。本文件细化阶段1—3和阶段转移；不得另建“每个候选正式A/B”的循环覆盖主线。

## 阶段1：硬件水平与使用目标

先读现场，再形成判断。按 [平台路由](platform-routing.md) 核对逐设备容量、计算架构、带宽/拓扑、CPU/RAM、软件栈、已有模型与入口。不把总显存简单视为任意可用的单块显存，不从显存容量推断kernel支持或实际传输速度。理论值与现场值分开。

复用用户已说的用途。缺模型/用途时简问主要工作、质量与等待取舍、上下文/并发与是否需要视觉；技术参数由AI结合调研提出，不能让操作者猜KV大小。常用任务细节可在阶段6确认。用户已指定模型就尊重选择，不能用小模型替换后声称同模型提速。

## 阶段2：六步调研

按 [调研与每周更新](research-and-weekly.md) 执行六步：同/异配置与速度案例；任务模型、量化与特别后训练版本；KV/量化管理/快照/卸载；草稿及新草稿；内核与显卡专属算法；有依据的ms汇总与方案。写入现有记录；周期任务按已选择的调研或自动优化模式执行，没有选择不阻塞当前工作。下文是证据和采用规则，不能替代这六步覆盖。

同硬件优先核对同架构、卡数、互联、显存改装、CPU/RAM与软件版本；完全匹配少时明确差异。同模型/同量化案例看实际执行布局、Draft和KV配置。不同硬件案例用于发现融合、数据布局、注意力、专家供给、通信重叠等可迁移机制，不按显存或理论算力比例承诺本机TPS。

检索当前原始模型卡、权重配置、engine发布/支持代码、具体kernel及Issue/PR讨论。关注源码实际分派、运行命令、计时边界、输入/输出、温度/思考、缓存冷热、并发和失败条件。首页、搜索摘要和“支持该模型”的名称不足以证明本机组合可用；高赞或维护者身份不代替复现材料。讨论有后续修复时读到与本机版本相关的更正。

没有指定模型时，跨发布者寻找适合用途和完整资源预算的候选，包含成熟路线，不只搜最新热门型号。给一个主推荐和有理由的备选，必要时比较少量候选；不为凑数量安装多套引擎。低显存先研究可用的小模型与量化，不因RAM大就默认推荐巨大CPU卸载模型；用户明确接受等待换质量时保留该选择。Base/Instruct/Draft、总参数/激活参数以及权重格式/实际运算精度都要分清。

用已有笔记记录：仓库/版本、实际借鉴文件或机制、案例条件与成绩、与本机差异、成功及反例。评论缺失只限制依赖该评论的结论，有本机源码证据的工作照常推进。不为简单明确修复凑论文、评论数或大报告。网络和下载问题按 [部署执行](deployment-execution.md) 处理。

### 实际采用的仓库点Star

把真正用于底座、内核、调度或直接指导实现的GitHub仓库列入采用清单；仅浏览过、无关或尚未采用的不批量点Star。在方案确认并采用后，用操作者已授权的GitHub账号点Star，已点过则保持，记录仓库链接及成功/已存在/待操作。执行本技能包含这项要求；宿主权限仍须满足，不创建账号、不猜凭据。无登录或工具能力时明确待操作者处理，继续部署，不让Star阻塞工程。Star不是采用许可证，也不能代替来源署名和版本记录。

## 阶段3A：可讨论的完整方案

形成具体方案，说明选择理由和主要取舍。尚未获得实施授权时，交给操作者讨论确认后再下载、部署和发模型测试请求；已有确认或明确选型实施委托时，记录选择后直接推进。自动优化中的新候选按已有授权范围裁决，不把阶段3A当成每轮必须请示的关口，见[自动优化与接续](autonomous-optimization.md)。

方案至少覆盖：

| 项目 | 应写清的内容 |
|---|---|
| 主模型 | 实际变体、版本、权重来源、权重量化、激活/计算路径，模型能力是否满足文本与视觉需求 |
| 草稿 | 草稿名称/版本、与主模型/tokenizer/验证器的兼容性、权重与计算精度、设备布局、依据案例选定的初始K；无投机时明确不适用 |
| KV与混合状态 | KV格式/精度、逐设备容量、页/块/检查点约束、单请求窗口与并发安排，GDN/SSM等状态独立核算，前缀保存恢复方式 |
| 底座与内核 | engine/fork/commit、实际构建、参考仓库及具体算子、Graph/并行路径，现成支持与需源码适配的缺口 |
| 视觉 | encoder/processor、分辨率策略、权重驻留或调入、图片特征复用、图片与文本前缀身份和边界 |
| 专家卸载 | 有此路径时写CPU/GPU分工、显存专家驻留/缓存预算、RAM权重及副本、传输与预取实现、指标入口 |
| 全部资源 | 主模型、草稿、KV/状态、专家缓存、视觉、Graph池、临时工作区、加载峰值和系统余量；逐设备核算，统一内存不重复计数 |
| 使用与实施 | 实际部署/权重路径、用户入口、下载与测试范围、原环境恢复办法，待操作者决定的实质取舍 |

KV不能只追最大容量。用目标上下文、并发、缓存复用和工作区共同决定；“能加载”“满载一次成功”“长短切换还能复用”分别验证。明确是否是每请求窗口、共享池还是静态槽位，不能把共享KV总容量当单请求上下文。

选量化要核对加载后的实际布局/算子，名称叫低位不代表主干或激活都按该精度执行。换量化是方案取舍，不能混入同精度kernel收益。前缀复用的必要状态不完整、每轮模板重建不一致等已知缺口应进入方案的修复项；不能先默认关闭缓存换“跑通”。

视觉默认保留。操作者需要视觉但所选模型/后端不支持时，提出兼容模型/已授权视觉路线等可行方案让操作者决定；不要偷偷关掉视觉或伪造“开图识别通过”。操作者明确选择仅文本用途/纯文本模型时记录视觉不适用，保留其选择，不额外换模型；后续视觉样例与放行条件相应不适用。没有可关闭思考的模式同样在方案中说明可行基准设置，不以隐藏面板或删除输出假装零思考。

## 阶段3B：确认后先完整部署，再进入短ms

方案确认不是部署完成。先按 [部署执行](deployment-execution.md) 完成安装/构建和整个服务组合，再做最小通路检查；第4阶段的短任务优化必须在这个完整组合上进行。

逐项核对计划值与runtime实际值：

| 组件 | 部署到位的证据 |
|---|---|
| 主模型 | 正确版本/量化已加载，实际计算路径和设备布局已核对 |
| 草稿与验证链 | 所选草稿、精度、设备和初始K已加载并启用，真实请求经过Draft/Verify；只有配置路径或模型文件不算。无投机方案明确不适用 |
| KV与Hybrid状态池 | 按确认的精度、目标池容量、页/检查点和并发分配初始化，前缀保存/恢复路径开启，实际生效窗口与预算核对 |
| 视觉 | 所需processor/encoder/路由及特征缓存配置到位；按需加载实现可用最小图请求验证，不要求为了检查永久驻留全部权重。明确文本限定方案记不适用 |
| 底座与内核 | 确认的版本/补丁已构建或安装并由目标进程加载；记录真实分派，具体性能与回退热点在阶段4细查 |
| 专家卸载 | CPU/RAM/GPU布局、专家驻留/缓存预算、调度/预取与采集入口已配置生效；动态缓存不要求预先装入全部专家 |
| 正式入口 | 客户端/API真正指向这套组合，最小请求可完成，进程与资源使用一致，无重复进程 |

不能用关闭草稿、缩小KV池、禁用视觉、临时换精度或简化后端的请求，代替完整部署后的基础ms测试。为了定位加载故障可单独检查组件，但这只是部署诊断，不能据此宣布阶段3B完成。自动fit缩小窗口、CPU卸载/精度变化或草稿静默禁用时，先纠正或回到方案讨论，不偷偷接受。

目标容量配置必须落地；lazy allocation的实现核对其有效容量与分配策略，不强制触碰每页/冷填满上下文。这里是部署与最小功能通路检查，不是长上下文压力测试、K扫描或正式性能A/B。确认整个组合生效后，才进入阶段4的短代码、传输等待与缓存测试。

## 未知主机的自主适配

将缺口落到具体层：二进制缺架构、模型加载/格式、某个算子、Graph捕获、并行分片、状态恢复、客户端协议。区分现成支持、可修复缺口、待探索实现和已证实约束；一次微测失败不能否定整条路线，能加载也不能证明高速可用。

方案允许源码适配时，先复现最小失败、修复直接缺口、检查实际生效，然后接入阶段4。不要反复重装或盲升驱动。硬件不支持某种原生精度与可通过转换执行该格式是两回事；标明真实执行路径及成本。改变模型、精度、KV预算或底座等实质取舍超出已确认范围时回到方案讨论，阶段内实现细节不反复问许可。

若不是局部缺口，而是整套设备后端、架构或大量算子待实现，按[后端移植分支](backend-porting.md)留在阶段3B研发。允许模块编译、参考数值与局部微测，按依赖推进；模块通过不等于完整部署通过。用户要求的原生投机、视觉、并行与容器语义均接通后，才进入阶段4整套短ms优化。

## 阶段推进与返回

- **3A→3B→4**：方案经确认或处于已有选型实施委托范围后完整部署。主模型/草稿/KV与状态池/底座内核/视觉/适用专家缓存按上表逐项核实实际生效，最小通路检查完成；固定初始K，温度0、零思考及视觉例外有记录。只写配置或临时简化运行不得进入4；完整部署不要求先跑满上下文。
- **4→5**：短代码实际可用；优化算子实际生效；重要传输/通信/等待已定位并处理或有明确必要成本依据；短前缀续接成立。缓存字段缺失先补可行的原生采集或轻量埋点；确实无法获取时按[指标受限规则](measurement-contract.md#内部指标不可获取时)继续独立工作，相关证据保留未验证，不能从“第二次快”宣称命中通过。若短阶段存在无法解决的实质限制，交付部分成果并讨论取舍，不能自动放行长测试。
- **5→6**：目标范围内上下文增长的主要ms来源、前缀破坏点和混合卸载竞争已处理或明确剩余限制，普通质量问题单列；没有理由必须测试全部标称窗口。
- **6→7**：操作者已指定任务，实际常用设置及生成后续接通过，其他部署组合确定；有思考模式并用于任务时检查高思考续接，无思考模式记相应项不适用。按API实际续接协议验证，不要求未提供的内部思考文本。没有投机机制直接跳过K调优并注明。
- **7→8**：任务内K选择及适用范围确定；正式对照不重启无限调参循环。
- **8→9或10**：只有操作者需要冷输入/prefill专项才做9，否则直接做10最终质量检查。
- **9→10→交付**：prefill改动及缓存复验完成后，在最终实际配置上做 [质量检查](final-quality.md)；质量未验收不能把全部优化称为完成。

如果后阶段发现算子回退、传输串行化或短缓存已坏，返回阶段4做最小复现，修好后重验受影响的长/真实任务，保留无关已通过成果。模型、草稿、量化、底座或状态布局发生实质变化时重新检查受影响阶段，旧成绩不能直接移给新组合。

## 草稿横向选择与训练边界

通常在方案阶段依据兼容性与原始案例选草稿。确需本机横向选择多个草稿时，先完成一个固定组合的短基础执行，再在明确范围内同任务比较各草稿的成本、有效输出和接受情况；选定后重新核实受影响的基础路径，再推进长阶段。它是明确的选型分支，不是因为接受率低就自动触发。

K调优统一留到阶段7。草稿训练、专家跳过、近似验证或降低目标精度不属于默认提速步骤；需要操作者另行明确范围。不能为了接受率放宽目标验证，也不能把草稿训练loss当实际部署收益。
