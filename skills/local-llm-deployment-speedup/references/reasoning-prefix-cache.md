# 长思考模型：思考内容、生成token与KV/状态快照的联合排查

用于长思考、高强度思考、工具间继续思考的本地模型，尤其是“前一轮想得很长，下一轮却重读整段”的问题。不是某个模型名称专属规则。先按[缓存破坏专项](cache-invalidation.md)确定计时和token口径，本章专查思考链与状态生命周期；历史实证见[案例C2、C3、C7、C8、C10](cache-failure-cases.md)。

**不能用普通回答、关闭思考的短样例或重复prompt证明长思考缓存正常。** 短阶段先查相关基本续接；到阶段5/6及用户指定的思考任务时，检查真实生成的思考如何成为下一轮输入，以及各组是否留有可恢复状态。已有长期任务优先读证据，不为制造样本强迫用户再跑一遍大任务。

## 1. 先确定该模型的思考往返契约

逐项核对目标模型、实际加载的chat template、reasoning parser及SDK/应用保存格式：

- 思考由哪个特殊token/前缀开启，如何结束，生成前缀是否已经包含半个think段或一段种子文字？
- 流中的reasoning/content/tool_calls怎样组合、保存和返回下一请求？界面折叠/不显示思考是否只影响显示，还是连保存/回传也删了？
- 普通用户新轮、同一用户任务中的工具返回、多工具并列、assistant续写/中断，各自怎样渲染？切换thinking参数是否改变旧历史或只改变新增生成前缀？
- 模型模板是否按设计丢弃某些旧思考，接口是否用会话句柄/opaque state延续，而非重传文字？允许复用的对象到底是文本、token，还是后端会话状态？

保持该模型实际协议与用户选定模式，不把所有模型都改成“永远回填全部reasoning”。模板按设计移除旧思考时，不能把不同输入的旧KV强行复用；可在协议支持范围内减少无谓重写、使用原生续接或明确其重算限制。API不返回思考原文时，不用摘要、占位文字或推测内容冒充原始思考；需要核对后端原始token/状态或该接口的续接能力。

这一步区分**协议允许的输入变化**和**实现不小心破坏前缀**，不是借模型差异直接放弃优化。实际模板/入口可修的重写、原token映射与状态保留继续往下查。

## 2. 沿一次真实长思考追到下一请求

选择原故障或同路径小规模复现，保留一次完整链路：

`runtime实际输入 → 原始生成token/流 → reasoning parser → API消息 → 应用持久化 → 下一请求投影 → 模板/多模态展开 → runtime实际输入 → 各组KV恢复`

对每一层只取定位需要的片段、token首差位置和计数；全文证据留本机供追查。必须连同工具结果一起使用实际SDK回放，不能用手工拼的“助手思考＋回答”替代实际消息格式。离线回放先验证上一请求的输入与线上一致，再评价修复候选。

按首个差异发生的位置处理：

| 首差位置/现象 | 排查重点 |
|---|---|
| 原prompt最后一个token或think开头 | 生成种子、前导空格、`add_generation_prompt`/续写设置、重复think标记 |
| 思考内部的第一个词/空白 | `trim/strip`、换行转换、解码清理、同文非唯一分词 |
| `</think>`及正文起点 | parser是否吞/补分隔符，模型种子是否被当生成内容重复插入，或真正生成的同文内容被误删 |
| 工具前后或第二个工具 | 多工具分隔、参数序列化、顺序和内部换行，reasoning与工具消息是否完整关联 |
| 只在新用户轮或thinking档位变化时 | 模板分支是否有意删除旧思考，应用是否重新投影全部历史 |
| token共同前缀完整，但cached停在旧prompt附近 | 跳过文本层，进入生成检查点、SWA窗口与快照依赖排查 |

只要前面一个token变化，后面大段思考就不能再按原前缀直接复用；不能因为“只是一个空格”把它当无关紧要。另一方面，实际共同token很多而恢复很少时，不再重复折腾模板。

## 3. 思考原token要与提交语义一起保存

推理模型生成的token可能存在多种同文切分。保留原始生成token的能力应覆盖当前请求真实交付/保留的reasoning、content和控制边界，而不是只保存最终答案。token恢复的适用检查与多模态偏移处理见[缓存破坏专项第3节](cache-invalidation.md#3-输入身份沿真实入口找第一个变化点)。

特别区分四个前沿：**模型已提出、验证已接受、状态已计算/提交、API已交付/历史已保存**。它们不一定同时推进：投机草稿可能被拒绝；EOS后的行不交付；停止字符串可能隐藏字符；最后一个采样token可能尚未再送入模型计算状态。

根据后端实际语义找到可恢复前沿，不能只凭`usage.completion_tokens`计算检查点位置。正确处理正常EOS、length、主动取消和工具结束；只保留已存在的部分状态，不伪造完整输出。旧Strata/NInfer映射只登记完整停止输出，而后续1Cat适配有不同登记范围，不能把一种限制推广为全部模型必须如此。

对于流式思考，检查应用最终持久化的是完整串还是仅最后delta；重连/恢复是否重复拼段、丢尾段或清掉reasoning字段。这些是按实际入口核对的分支，不声称所有客户端都存在此bug。先比对原HTTP流与下次请求，再判断责任在客户端、parser还是引擎。

## 4. 长生成期间是否真的产生了可恢复快照

对若干实际生成边界记录：请求已计算位置、已提交位置、保存的checkpoint位置、每组可恢复位置、生成结束后的最晚共同边界。只看“模型输入支持256K”或“总KV还在”不够。

重点读保存条件与调用时机：

1. 是否只在prefill的`prefix_cache_boundaries`保存，而decode不再形成对齐检查点？历史安装版曾有`step_end < num_prompt_tokens`条件，解释了token完整但cached仍停较早边界的现象；不能未跟踪状态就把每个剩余miss都归因它。
2. 投机一步跨越多个边界时，保存的是哪个已接受位置？EOS/拒绝/length截停后是否把快照挂到了未提交的未来位置？
3. GDN/Mamba/卷积state是否与Attention KV、SWA窗口、位置和页表属于同一逻辑前缀？只保存最终state不能恢复任意较早分叉，不能通过裁切一个state tensor“退回”历史。
4. 状态ring轮换时，仍被快照或Graph引用的槽位是否被下一轮写入？复制/旁流是否完成后才登记可恢复？请求回收时metadata是否清理？

如果确有必要增加生成检查点，优先沿用底座现有提交与对齐机制，在真实需要的边界保存；不要每token拷贝整份GDN状态，制造新的轮时和显存成本。一起衡量快照保存/恢复耗时、完整轮时、实际复用位置和资源余量。

## 5. 快照存在，不代表长思考结束后还活着

在“刚保存”“又生成一段后”“结束/释放请求后”“另一个请求运行后”“下一轮查找时”观察同一候选边界，找第一个丢失事件。最小埋点可记录request/组/boundary、block或state版本、refcount、分配/释放/回收原因；无需把全部GPU张量或全部日志送入上下文。

按依赖链检查：

- **FullAttention前段页**是否被快照引用，还是只有末端状态被留住？C7证实过后者。
- **SWA生成窗口**是否被当成“过期，未来无用”而优先回收？C8中原prompt窗口保留，最近生成检查点的窗口有一块被覆盖，造成整体退回旧prompt。
- **GDN/Mamba检查点**是否仅保留最新状态，而工具续接/摘要分叉需要旧边界？多组是否能在同一位置相交，而非各有一份不同位置的state？
- 快照LRU淘汰是否一起释放依赖？最长失效后是否继续找较短有效项？共享完整页与复制尾页的计数和总容量是否正确？
- 一轮长思考是否跨过token映射缓存上限、检查点保留上限或状态ring寿命？若因明确预算被淘汰，报告哪层容量，不把它误写成模板bug。

token映射、KV依赖引用、普通LRU优先级和固定pin是不同手段。根据首次丢失原因修复，不一律加内存或无界锁住历史。反过来，确认是新草稿/Graph/专家挤占之后，也不要坚持只改模板而拒绝重新预算。

## 6. 思考任务的针对性验收

默认先使用约10k输入和足以触及原故障的真实生成量；具体思考长度沿用户任务，不把强行填满65K输出、近满上下文冷prefill列为固定门槛。已经有长思考历史时优先使用其真实token与状态证据。仅用重复空格等构造样本能证明分词分支，不能代替自然思考/工具链。

按改动选择这些有区分力的场景：

- 正常思考结束并回答，再追加一个短问题；检查旧输入、整个已保存生成段和实际KV恢复位置。
- 长思考后调用工具，实际执行并回传结果，让模型继续；有多工具/继续思考用途时覆盖对应消息形式。
- 生成跨过原故障checkpoint边界，再在结束后续接；边界前后各取必要样本，核对每组状态，不只看cached总数。
- 原故障涉及length/取消/拒绝时，复验同一结束方式，并区分完整输出与部分输出的合法尾算。
- 涉及回收或资源时做A长思考→B→A、长→短→长；涉及图片时保留旧图再追加/换图，不删除原图制造命中。
- 改模型、草稿/K、思考模式、模板/parser、状态快照或池预算后，只复查受影响的这条链；已有可信成果继续复用。

每组记录：原输入长度、实际生成思考/正文/工具的可获得计数、下轮共同token边界、各组最晚共同恢复边界、实际cached/新计算、TTFT和整次任务结果。计数不可得就注明，不按文本长度猜token；不同后端的“输出token”和“已提交token”不要混用。

必要的冷热正确性对照应使用相同模型、输入、图像、设置和合适输出范围；若输出不同，结合浮点/采样、实际状态与受控数值检查定位，不能只凭一次措辞不同断言缓存损坏，也不能只看措辞正常就验收错误状态。

## 7. 什么才算这一问题处理完

能用证据回答：**思考是否按该模型协议保留 → 实际token是否按预期延续 → 每组在同一边界是否有状态 → 依赖在请求结束及相关切换后是否存活 → 真实续接是否减少了异常重算且任务正确。**

若只修好其中一层，就继续检查原故障是否仍存在；剩余合法块尾、明确容量界限和协议性前缀变化单独说明。C3的原token恢复成功后仍出现C8的滑窗回收故障，正说明不能在“文本/token已对齐”处结束验收。

不能以关闭思考、降低用户指定强度、清历史、删除图片或绕开工具任务来宣称解决。高命中下模型仍在一次生成内重复思考是另一类故障，按真实完成状态处理；不要把它当成KV miss，也不要将有工具调用但未执行的回放说成原任务已完成。
