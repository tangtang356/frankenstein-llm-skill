# GitHub源码对照：从当前瓶颈到可实施候选

用户要求仓库对照，或自主优化需要外部实现依据时读取。接入[六步调研](research-and-weekly.md)与[自动优化](autonomous-optimization.md)，不另建阶段审批，也不每轮扫描所有仓库。目标是判断当前部署缺什么、能借鉴什么、怎样验证；报告新版本或罗列热门仓库不算完成对照。

## 1. 先确定要比较的真实执行点

复用原部署记录和已有性能证据，核对模型/量化、硬件、输入shape、当前耗时、运行器和实际加载产物。原始commit、安装包版本、本地补丁、构建结果和正在运行的版本分别记录；同一上游commit不代表部署代码未修改。只读任务不加载模型或开新采样；暂时无法读取目标机时仍可查公开实现，但明确“未与当前运行代码核对”。

将问题缩成具体机制，例如：九行拒绝采样回读、同输入多投影重复转换、GDN准备晚绑定、长注意力分区、Graph补齐与重放。已有下一步且依据充分时先继续工程，不为了形式先做一次全网调研。

## 2. 选择相关仓库并锁定阅读版本

还没有来源仓库时，先按[发现与筛选](research-and-weekly.md#先发现有用的实现再收敛候选)从成本构造机制词，跨设备/模型检索并追踪依赖、fork和原始实现；本章的代码对照不能代替发现新来源。

当前引擎上游、已采用fork和实际依赖用于判断已有能力；同时按瓶颈查其他引擎、其他模型和硬件上的可迁移部件。有明确来源线索就直接查，不必等本引擎上游查完。Strata、1Cat、Basalt、Radiance、NInfer、vLLM、llama.cpp、FlashInfer、草稿实现等是按现场选择的来源，不是每次必须全读的清单。不同硬件可以借鉴机制，不能直接移植不支持的指令或照搬其速度。

优先用宿主已有GitHub连接器；能力不足再用官方网页、仓库API或已安装git。先检索文件名、函数、真实kernel名、错误文本和相关PR/Issue，再读取命中文件及调用者。空搜索结果、索引延迟、权限错误或旧路径404，不等于功能不存在；用符号搜索或当前文件树定位，避免下载所有源码才开始判断。

保留仓库、完整commit SHA、关键文件/函数和必要行号，公开证据链接固定版本；记录核对日期。对同一仓库/共享历史的fork可比较上次读取commit到本次head的相关文件变化；跨无共同历史的引擎按机制和接口比较，不硬做git commit差异。PR标题、关闭状态、release说明仅作线索，核对变更是否真的进入当前阅读版本，以及后续修正/撤回和相应测试。

整仓库排名不决定组件价值：可以保留当前运行器，从另一仓库取视觉塔、collective、量化计算、注意力或状态机制。跨仓库候选写清宿主保留什么、来源提供什么，以及直接移植还是机制改写；具体接法与历史成功/撤回案例见[跨仓库组合](cross-repository-composition.md)。不要求来源仓库先完整支持当前模型。

对有速度优势的候选，先按[快因分析](cross-repository-composition.md#找到快的原因再决定如何移植)区分少读写、少计算、更高利用率、重叠等待或缓存复用；落到代码和本机成本后，再设计移植。没有目标设备适配时拆解算法/布局与硬件专用实现，写出本机替代路径，不能仅按支持列表筛掉。

## 3. 沿调用链核对实现，而非只找到同名函数

按当前问题追到必要深度：**调用入口 → metadata/布局准备 → 条件分派 → 实际算子/Graph → 状态提交与消费者**。对应核对：

- SM/指令、dtype、量化码与scale、M/N/K、stride/对齐、TP/路由和KV格式是否匹配；不匹配是需要适配还是不可用，写出具体原因。
- 开关默认值、注册/构建条件、加载路径、依赖库版本和fallback；源码存在不等于安装包编译了它，更不证明当前服务调用它。
- Graph采用的逻辑/补齐尺寸、计划与重放边界、工作区和mask、跨流/卸载同步；尺寸固定不证明动态内容可跨请求复用。
- 所需配套修改和验证代码：调用者、kernel、缓冲/布局、构建和状态语义可能组成一个完整改动包。不能只抄一个函数并删guard强行接通，也不默认整套升级抹掉已有补丁。
- 对方benchmark的硬件、输入/输出、轮数、冷热/Graph、计时边界及数值检查。kernel成绩和端到端成绩分开；没有同口径依据就写待测，不承诺本机省多少ms。

只为定位读取相关测试/复现和必要Issue后续，不把每次普通性能修复扩成完整仓库审计。具体机制仍按[毫秒主章](millisecond-optimization.md)、[实测补充](millisecond-case-lessons.md)、[长注意力](long-attention-optimization.md)或缓存专项实施。

## 4. 对当前部署作差异裁决

在原记录用几句话或简表写清即可，不要求JSON或新状态系统：

| 裁决 | 后续行动 |
|---|---|
| 本地已有且实际生效 | 复用结果；不要因为上游新命名或不同commit再做同一优化 |
| 本地已有但未编译/加载/命中 | 优先修加载、分派或配置链，验证实际执行，不先重写kernel |
| 本地缺失且条件相符 | 列需要移植的完整配套改动和最小验证，授权内直接实现 |
| 仅部分形状/设备可借鉴 | 做条件适配与正常回退，不能声称全局可用或直接升级即可 |
| 收益不明、条件不符或旧问题已修复 | 记录证据与再次考虑的触发条件；不反复测试，不把旧Issue当当前缺陷 |

候选最少连起：**本地瓶颈/证据 → 固定版本源码入口 → 本地与上游差别 → 可改机制/依赖 → 验证方式及取舍**。没有本地现场证据时只能给“候选/待适配”，不能填“已缺失/已生效”。

## 5. 自动实施与后续增量

已授权自主优化时，按实际任务收益、实施成本和证据强度选择候选，连续实施、验证和保留/撤回，不在报告末尾统一退回“是否继续”。测试仍按主流程：必要局部正确性和短完整轮反馈、受影响缓存/功能，正式比较集中在阶段8；不因仓库提供大benchmark就自动冷填满窗口或重跑长任务。

仅调研时止于对照结论，不自动下载权重、构建或发模型请求。正式切换、系统变更等沿用既有范围，不因发现仓库新版本扩大权限。实际采用的来源按主流程记录署名/许可证和点Star；只浏览过的候选不批量Star，不自动向上游发评论或PR。

把已查commit、相关路径、候选状态/否决原因和下一步写回原部署说明。下次只查相关变化；上游没变但本地shape、依赖或瓶颈变了，可重新评估旧机制。既无新证据也无未完成工作就结束本轮；API限流或访问错误记为“本次无法核查”，不能记作“没有更新”。不为资料获取失败阻塞已有证据足够的工程。

## 本轮公开源码核对示例

核对日期2026-11-11；以下证明如何做代码对照，不是目标机移植或性能验收，不要求升级到这些版本。

**1Cat：没有增量就复用。** API比较`1CatAI/1Cat-vLLM`已记录的`75e51a5bc405e85c15a7060f28c12de6ace56655`与本次`main`返回identical、0个新增提交。[固定版本](https://github.com/1CatAI/1Cat-vLLM/tree/75e51a5bc405e85c15a7060f28c12de6ace56655)只说明该分支没有变化，不证明本地补丁等于上游，也不覆盖其他分支。

**vLLM：Graph分派不是只有开/关。** 在`3c5cdcfee76bbd4fd26a77fd2b97520ecaa78e38`的[CudaGraphManager.dispatch](https://github.com/vllm-project/vllm/blob/3c5cdcfee76bbd4fd26a77fd2b97520ecaa78e38/vllm/v1/worker/gpu/cudagraph_utils.py#L558)，按实际请求、token、uniform query及其他兼容条件选择已有图；不匹配才返回NONE。输入token可能已补齐。由此可提出检查“真实有效行数与图执行尺寸、padding及捕获集合”的候选，尚不能说某台机器有同样浪费。旧`vllm/v1/cudagraph_dispatcher.py`在该快照404，按`CudaGraphManager`重新搜索找到上述入口，不能沿用失效路径断言能力消失。

**FlashInfer：性能分区与正确性一起看。** `cfa0318a1316e8838bdee32c2a2014e22001dabe`的[scheduler.cuh](https://github.com/flashinfer-ai/flashinfer/blob/cfa0318a1316e8838bdee32c2a2014e22001dabe/include/flashinfer/attention/scheduler.cuh#L909)在Graph计划中分配并填充有效块mask，防止补齐CTA读取未初始化的计划尾部；不能只复制缩减grid的想法而漏掉mask/plan约束。[Issue 4002](https://github.com/flashinfer-ai/flashinfer/issues/4002)提供特定FA2路径和历史版本的复现背景；本次读到的代码已有相关保护，不据旧报告宣称当前版本仍缺mask，也不把H100复现的数字外推V100/2080Ti。
