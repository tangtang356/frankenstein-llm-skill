# 阶段4：短任务完整轮次ms

**先把短的做好，再去长的。必须细查全部传输和等待，不能只盯GPU计算。** 前阶段必须已经在方案确认或已有自主实施委托范围内完成整套部署：主模型、草稿、KV/状态池、底座内核、视觉与适用专家缓存实际生效，不能拿缺组件的临时配置进入本阶段。当前只解决固定组合的基础执行浪费，不扫K、不追接受率、不跑正式统计A/B，不提前做长上下文或冷prefill专项。

## 固定一个可解释的短基准

温度0、关闭思考、视觉开启；固定主模型/草稿/精度/K、模板、输入、输出预算、并发与缓存状态。核对服务有效配置和真实输出，不能只看请求参数。模型不能关闭思考时按阶段3已讨论的例外执行，不把隐藏思考当关闭。

同时核对实际payload及应用默认注入的惩罚、logits processor、grammar/结构化输出和验证采样方式；这些选项可能让投机、Graph或流水线回退。阶段4固定它们，修其执行成本，不擅自删掉用户需要的能力。相关反例与排查见[请求选项](millisecond-case-lessons.md#1-请求选项会改变执行图采样惩罚与语法也要查)。

先用 [短测试材料](../assets/short-tests.md) 或项目已有等价短代码任务；没有另定规模时可用约0.5–2k输入token、128–512输出token作为起点，按实际tokenizer计数。这是可调整起点，不为凑token填充垃圾，也不强行拖到输出上限。自然结束与固定计时窗口分开，输出长度变化不能冒充kernel加速。

短代码主基准保留视觉能力开启，并另跑一项真实小图识别及带图续接。纯文本请求不能证明视觉路径经过验证；每轮都反复编码新大图又会掩盖decode，所以视觉首用、重复图、换图分别记录。不能为漂亮的ms关闭需要的视觉路径或降低用户图片精度。阶段3明确的仅文本方案不跑图像用例并标不适用；不能把未测写成图像已通过。

热态先完成必要加载/编译/Graph预热，记录首次请求成本；权重驻留、专家缓存热态、Graph暖态、前缀命中是不同状态。首次无共同前缀请求与后续复用请求分开，不清除共享生产缓存制造冷态。

核对测量时CPU运行状态、各rank工作分配、GPU时钟/温度/功耗、队列及其他负载；与基线不同就记录，不能把调频/排队变化当kernel收益。主机collective调用长也可能在等另一rank，按时间线归因，不先改绑核、系统设置或认定互联故障。

## 完整轮次边界

从实现确定本轮需要的输入准备、Draft、Target/Verify、接受/采样、通信、状态提交以及进入下一轮的必要工作。Target与Verify可能是同一段；重叠工作不可重复累计。普通解码用完整step；投机解码用完整round，并记录实现边界。

连续稳定窗口覆盖多轮并考虑首尾排空。把准备前移、工作延后或预取搬到另一线程并不代表它消失；用同一完整窗口验证是否真正缩短关键路径。异步并发轮次不能简单求和作为总墙钟。

主机单调时钟测提交/调度/请求墙钟；GPU事件测同一设备的事件区间，读取前确保结束事件完成。host enqueue时间不是GPU完成时间，事件区间也可能包含空隙和等待。多stream结束边界须覆盖必要依赖，多卡单rank结束不等于全部输出就绪；不同GPU事件不能直接相减。

不在每个算子/token间新增全局同步去“测准”，那会破坏本来要优化的重叠。使用现有计时、预分配事件、延迟读取和短trace；诊断时改变了同步条件要标明，最终读数关闭重型profiler并恢复真实路径。参考 [CUDA异步语义](https://docs.pytorch.org/docs/2.15/notes/cuda.html) 和 [Event API](https://docs.pytorch.org/docs/stable/generated/torch.cuda.Event.html)，实际调用匹配安装版本。profiler退出后进程也可能持续变慢，详见[低扰动测量与进程状态](millisecond-case-lessons.md#7-低扰动测量不止关掉profiler查进程残留与未覆盖路径)；干净进程复核遵从已有服务窗口，并恢复可比冷热条件，不能擅自重启。

## 必查的传输、等待与算子

沿一条完整执行链检查，而不是只挑最慢kernel：

| 区段 | 查什么 | 常见可行动方向 |
|---|---|---|
| CPU准备 | 模板/分词、tensor构造、metadata、重复扫描/序列化、rank调度与调频 | 共用当轮准备、可提前项与动态晚绑定项分开，避免重复构建/转换与复制 |
| 主机与设备传输 | H2D/D2H字节、次数、pageable/pinned路径、每轮小拷贝、隐式取值同步 | 减少搬运与同步，复用驻留数据，核对生命周期 |
| GPU间传输 | 真实P2P路径、collective、rank到达偏差、是否绕CPU | 匹配分片/拓扑、减少暴露通信，保持必要依赖 |
| 专家供给 | 显存专家缓存、CPU/RAM计算/读取、预取与换入换出 | 见下节，按实际阻塞毫秒优化 |
| 计算路径 | 实际shape/dtype/量化scale、stride、调用次数、kernel分派、Graph是否捕获/回退 | 共用输入准备、模型专属融合、窄shape路径，保留尺度与舍入语义 |
| 采样与接受判断 | 惩罚/grammar/mask、草稿CPU回传、逐位置循环、小标量回读 | 核对真实请求分支，减少无谓同步并保持验证与格式要求 |
| 状态提交 | KV/Hybrid快照、复制、检查点、提交/拒绝分支 | 去重复，保持正确可恢复边界及地址/所有权 |
| 重叠与主机间隙 | 旁流依赖、同步点、线程调度、launch间隙、跨轮准备 | 减少串行空隙；不能删除必要同步制造竞态 |

每个主要区段记：实测ms、计时边界、传输量/次数（适用时）、重叠对象、暴露在关键路径上的等待、已做处理和剩余原因。已有日志或简表足够，不要求填完统一schema。总墙钟与分项不能强行平账，嵌套/重叠/未知保持原意；CPU等待与它等待的同一GPU工作不能重复算节省。

不仅检查参数写了什么，还要用已加载库/编译产物、分派日志或trace确认优化算子真正执行。某一shape快不代表所有shape快；窄分派应保留其他shape的正常回退。Graph capture成功、replay实际生效和旁流buffer正确性分别核对。

从主要区段形成最小成本图：实际调用次数与形状、同设备/同rank时序、跨流和跨轮依赖、暴露等待、可改机制及预期影响。小回传先找阻塞依赖，不能按字节量排除；把单次微核收益乘调用次数也只是候选估计，还须扣掉重叠与新增准备/同步成本。嵌套累计不能当可追回时间。详见[实测实施细节](millisecond-case-lessons.md)。寻找外部可迁移实现时走[GitHub源码对照](github-runtime-comparison.md)，按[跨仓库组合](cross-repository-composition.md)吸收适合当前瓶颈的内核、通信或模块。比较组件接入后的净成本；沿用有效底座不等于只能用该仓库自己的实现。

## Graph已生效后：检查补齐工作与计划成本

同时记录实际有效请求/行数、补齐后的输入或Graph尺寸、实际执行模式和plan/capture/replay次数。Graph可重放仍可能使用过大的捕获形状、过多无效tile/CTA，或在外部反复重建计划；首次编译/捕获与持续每轮开销分开。先确认现场有这些成本，再优化捕获集合、准备复用和条件分派，不无条件捕获所有shape或强开FULL。

padding有效mask、页表、动态长度、工作区和跨流依赖要与图尺寸一起保持正确；不能删掉mask/同步换取表面提速。图更多还可能占用KV/专家所需空间，最终看完整轮和续接。具体源码线索见[GitHub对照示例](github-runtime-comparison.md#本轮公开源码核对示例)，只读核对不等于本机已发现或已修复问题。

## Strata类CPU/RAM/GPU协同：专家缓存必查

按实际runtime查实现，不能凭名字假设卸载方式。若确有专家驻留/动态缓存，在短阶段就采集：

- **命中口径**：请求了哪些专家、哪些已驻留、命中/查询/未命中计数，按请求或阶段窗口取增量；注明是路由选择次数、唯一专家数还是字节口径，不能混算。
- **供给成本**：未命中后是CPU计算、调入GPU、磁盘读取还是其他路径；记录实际传输字节/次数、换入换出、CPU准备/计算和GPU等待。RAM缓存命中不等于显存专家命中。
- **预取与重叠**：预取命中、按需命中、无用预取/淘汰按实现分开；核对传输覆盖了多少计算、仍暴露多少等待。高命中率不自动等于低ms，投机预取多搬的数据也计成本。
- **共同预算**：专家缓存与KV/状态、草稿、视觉和工作区共同占用的内存，观察短任务初始和稳定阶段；提高专家命中不能靠驱逐有效前缀。静态专家驻留仍检查GPU路由覆盖、CPU供给/计算及搬运等待，只有确实不存在的动态换入/淘汰字段记不适用；不能因没有动态缓存跳过整条供给路径。没有专家卸载机制才有依据地将该专家分支记不适用，Dense卸载仍查传输。

指标缺失时查原生日志/源码或加最小埋点，不用GPU利用率反推命中率，不建设新监控平台。区分冷填充和稳定运行；阶段4验证供给机制，阶段5/6再验证长上下文及真实任务改变后的访问分布。

## 按依赖组成可运行的优化包

以当前关键路径决定顺序。有专家卸载且供给等待占主导时，按“供给 → 实际计算 → 调度与状态”推进：先把CPU/RAM/显存专家通路做好，再适配占时的矩阵和草稿头，随后配平双卡、减少交接空隙和状态复制。Dense或供给已非主导的部署直接处理自己的大头，不机械重做专家优化。一个阶段改变了成本分布，就重新看下一段成本。

大页、交换缓冲轮换、驻留适配频率属于可能相互依赖的供给组合；只测大页而未接通交换与驻留，不足以判断完整路线。按依赖完成必要构件后做一次短整合反馈，已有正确性检查继续复用。单项微测用于选实现，完整轮时用于判断是否值得保留。

同样，双卡分工要把草稿算进去；快照优化可以改变保存方式，而不删状态。具体实施见[IQ3工程拆解](optimization-engineering.md)的专家供给、SM75、双卡流水线和GDN章节；数值进展见[Python案例](case-swift-iq3xxs-python.md)。可直接复用[历史12函数题](../assets/python-round-baseline.md)。

跨group公共准备、下一轮预备项与Prefix Align兼容、小DtoH控制依赖、九行快路径覆盖、Pi独立尺度融合、Ripple输入准备复用与跨卡事件，按[实测补充](millisecond-case-lessons.md)的相应节实施。减少同步须落实生产者/消费者与缓冲所有权；局部融合保留中间舍入和各尺度，实际数值/状态及回退分支检查与改动匹配，不以少量生成文本正常代替。

## 短缓存验证不可省

至少跑：首轮短代码 → 带上实际生成内容追加一个修改要求 → 再追加一次。记录真实命中token、查询token、新处理token与首内容时间，核对返回内容属于当前会话。不同后缀和不同前缀用于识别错误的响应缓存；带图路径另查同图复用与换图失效。

不要用“相同prompt发两遍更快”代替生成后续接。温度0不证明跨设备/不同实现必然逐字一致；前缀token与状态正确性要查实际序列/恢复边界。细节见 [上下文与缓存](context-and-cache.md)。改传输、状态、Graph或缓存路径后重验相关短续接；只改文档不发模型请求。

## 前期反馈与放行条件

每次明确修复后看实际生效路径、相同短任务ms、输出与受影响缓存，保留必要前后读数。不反复切回旧构建跑正式A/B，不每改一点跑全部长任务，不对每个小收益做统计认证。数据反常或明显退化时做最小复现并修复/撤回；未确认的变化标“初步观察”，不宣传精确收益。局部筛选已明显退化且无其他必要收益的候选可直接停止，不为凑流程跑长任务；微测获胜还须看真实覆盖和完整轮净收益。旧候选只有依赖图、shape、版本或证据改变才重新评估，见[保留与撤回案例](millisecond-case-lessons.md#8-局部正确或更快之后如何决定继续保留或撤回)。

本阶段固定草稿和K。有效提交token可记录以识别输出/轮次数变化，不能把这一记录变成接受率调优或自动K扫描。没有真实低层计时只能报告现有请求层数据，并补可行定位手段，不能从TPS和未知接受数捏造整轮ms。确实无法访问内部指标时，按[指标受限规则](measurement-contract.md#内部指标不可获取时)继续独立验证并保留证据限制，不把“不可观测”写成“没有问题”。

进入长阶段前，必须能回答：主要传输与等待分别是什么、处理了什么、剩余为何必要；实际优化算子是否执行；短代码与所需小图是否可用（已确认文本限定方案的图像项不适用）；实际生成后的短前缀是否复用；混合卸载时专家供给是否查清。**短的未做好就继续查短的，不用长测试拖延基础问题。** 无法解决的实质限制要交付证据并讨论取舍，不能声称已优化到极限，也不能无限无依据扫参数。
