# 长注意力专项：从长度衰减到实际内核优化

在阶段5发现decode随历史增长变慢，或用户明确要求修复长上下文性能时读本章。沿用已有部署、短阶段成果和授权，不重新走完整流程。这里优化全注意力的执行成本；前缀复用、新输入prefill、Hybrid状态恢复仍按[上下文与缓存](context-and-cache.md)分别处理。

按需跳转：先定位 → 分块与归约 → KV读取 → 分派与Graph → 生效和验收。具体仓库、文件、符号与历史实测见[仓库实现案例](long-attention-cases.md)。没有目标机时可以完成源码方案，不能声称已提速。

## 1. 找到随长度增长的那部分成本

从实际请求记录模型、主/草稿版本、GPU架构、TP、KV dtype与scale、page size、每卡Q/KV头数、head dim、batch、query rows、可见KV长度和Graph模式。投机验证的query rows可能是多行，遇到EOS/拒绝后还有尾宽；不能只测单token decode。不要把q8查询八行和8-bit量化混为一谈。

在常用长度附近选择少量位置：默认可从约10k输入起步，已有暖历史可直接复用；跨过怀疑的分派阈值时看阈值前后。接近满窗口冷填充只有纳入用户范围时才做。固定模型、草稿、K和基准设置，分别记录：

- 注意力主体、局部结果归约、页表/metadata准备，以及KV搬运或格式转换。
- 完整执行轮次、每轮有效提交token和真实任务速度；普通decode与投机轮次口径分开。
- 实际命中与新增计算、显存占用、专家供给等待；仅有高前缀命中仍要每轮读取可见KV。

若是检查点复制、专家被挤出、CPU重复扫描或抢占主导，回对应章节修复。多卡/多流kernel累计时间不能直接当墙钟成本；看关键路径和暴露等待。注意力只占小部分时，不因发现一个新内核就长期扫参数。

## 2. 分清三种“块”，再选择改动

| 名称 | 改的是什么 | 通常影响 |
|---|---|---|
| KV page/block size | 缓存物理页和映射粒度 | 页表、碎片、Hybrid检查点对齐、前缀池容量 |
| kernel tile，如N32/N64 | 一个线程块内一次处理多少key | 同步次数、共享内存、寄存器、访存复用 |
| split-KV/partition | 同一query/head的KV序列交给多少线程块 | 并行度、部分结果工作区、额外归约 |

三者有约束但不是同一旋钮。先沿用现有分页和精度，确认该shape缺并行度、循环/同步过多，还是读取效率差，再改对应部分。不要把page size改大误称为tile优化，也不要把chunked prefill写成decode split-KV。

## 3. 分块／分段注意力与并行归约

长KV、少query/少KV头时，单个线程块扫描很长的序列可能没有足够并行工作。split-KV将同一头的**全部可见KV**分给多个线程块，各自产生softmax统计及局部输出，再合并。它不要求删历史或近似稀疏化。

实施时沿调用链找planner/launcher、partial kernel、merge/reduce、scratch分配及Graph捕获，而不是只改split常量。先用当前方案和少量由SM数量、batch、KV头数、tile数推导的候选；不做无边界网格搜索。

- split太少：可运行线程块不足或单块循环过长；适当增加可能有益。
- split太多：每块工作太少、尾块浪费、partial写回和归约增多；此时减少split或扩大tile。
- tile变大：可能减少加载/同步，却增加共享内存和寄存器，降低驻留并行度。分别看主体、归约和两者总时长，最终落到完整轮次。
- 多请求、多KV头已经提供并行度时，单请求长上下文的最优split通常不能直接套用；投机多query行也要重新核对。

**归约必须保留softmax的权重。** 以自然指数表示，分段保存最大值m、未归一化分母l和向量a：合并时先取全局最大值M，再用exp(m−M)重标定各段，输出为加权a之和除以加权l之和。若部分结果已归一化，则用对应LSE求合并权重，不能直接平均输出。实现可能使用exp2/log2，缩放必须一致；检查全mask/空段、尾页和极大logit，避免inf−inf及除零。

保持当前累加精度与必要补偿；调整归约顺序可能改变浮点结果，不能凭文本看起来相同认定逐位等价。用相同Q/K/V和mask对可信参考比较绝对/RMS误差与有限值，阈值按原实现精度及任务要求选择。长序列参考太贵时抽取完整可见历史上的少量query/head，不偷偷截断历史后宣称长注意力正确。

可直接研究：FlashInfer的`SingleDecodeWithKVCacheDispatched`及`MergeStates`；llama.cpp的`launch_fattn`、`flash_attn_combine_results`；vLLM历史V1/V2分派。对应版本链接见[案例B至D](long-attention-cases.md)。

## 4. KV读取布局、分页与GQA复用

先打印实际shape、stride、物理页映射、对齐、dtype和scale位置。区分逻辑布局与物理连续性：NHD/HND是接口约定，不能只改字符串而不改变实际数据。检查消费者是否按head dim连续读取、相邻线程是否合并访存、GQA多个query头是否重复读同一KV。

候选通常按成本从低到高选择：

1. 去掉每轮重复gather、全历史transpose和临时materialize，让kernel直接按现有page table读取。
2. 在寄存器/共享内存预算内复用同一KV tile，服务同组query头或多query行；并行度与复用之间要取舍。
3. 对已知page size简化页定位、缓存合理数量的page id、合并载入；尾页仍按实际长度mask，不越过已提交边界。
4. 若需要改KV存储布局，同步修改写入、读取、页复制/恢复及相应Graph参数。把迁移或转换耗时计入，而不是只报新kernel时间。

FP8/INT8 KV的读取包含解码与scale处理，不是存储字节减半就必然快一倍。SM70使用FP8存储不意味着具备新架构的原生FP8算术。优先在既定格式下改善读取/解码；降精度、滑窗、稀疏丢token、改变RoPE或上下文容量属于不同取舍，不能混入等语义执行优化。

变更工作区或页粒度后复核KV/Hybrid检查点与专家缓存的共同显存预算；局部更快却挤掉暖前缀导致重算，应以实际任务结果裁决。

## 5. 按实际shape分派，兼顾短长和Graph

分派依据至少覆盖当前实现真正使用的条件：设备/编译架构、dtype、head dim、Q/KV比例、page size、batch、query rows、可见长度、mask/窗口和Graph能力。记录命中条件及fallback原因。阈值来自目标版本与目标机读数，不把仓库中的4096、8192、80 splits等写成通用建议。

通常保留短上下文的轻量路径，长上下文进入分段路径；不支持的shape使用正确fallback。先检查后端已经有的快路径是否因加载器、页大小、尾宽或模板条件没接上，再决定写新kernel。

CUDA Graph需要同时处理**容量**与**实际有效长度**：

- 捕获时的grid、partial buffer和页表容量要覆盖声明的重放范围；实际长度变化后无效split/行不能读取上次残留结果。
- split策略在长度阈值可能跳变，不保证单调。对每个Graph区间核对边界和区间内分段极值，不能只用最大长度对应的split数量分配。
- buffer地址稳定不足以证明数据归属正确。多流、并发请求、不同graph版本及旧图仍引用的工作区，需遵守消费者完成前不覆盖的规则。
- 固定batch不代表变长KV能重放同一启动计划。检查planner是否需要重做、是否退出Graph及CPU开销；不要在capture内临时分配或引入同步来掩盖问题。

NInfer有按执行区间计算split容量的实现；1Cat有query rows、page、capacity及算子revision检查；FlashInfer明确说明固定split与Graph并非自动兼容。见[仓库案例](long-attention-cases.md)。

## 6. 证明“新代码真的被运行”

按可获得证据完成这条链：源码commit/补丁 → 构建产物路径与hash → 活跃进程加载的库/模块 → 该请求shape的真实分派 → GPU trace中的主体与归约kernel → 完整轮次结果。

环境变量、编译成功、启动日志“enabled”只证明其中部分。可用现有日志或最小一次性分派计数补证；Graph重放时Python入口日志不等于每轮kernel，抽样GPU trace确认。Profiler仅用于定位，性能读数另取无profiler开销的运行。内部不可观测时按[测量约定](measurement-contract.md)明确未证实部分，继续可做的功能与任务验证。

一个最小实施记录用TXT即可：实际shape与瓶颈；来源版本/修改入口；新旧kernel及分派；主体+归约/完整轮时；正确性、续接结果；保留或撤回原因。不为此新建benchmark平台或schema。

## 7. 用小范围证据完成，再继续真实任务

新增内核先过代表性数值检查，再用目标服务做短反馈；以下按改动触及范围选择，已有可信结果可复用：

- 页尾、tile/split尾部、分派阈值两侧；实际batch与投机query尾宽。分页改动至少有非连续物理页映射，不能只测恒等页表。
- eager与实际Graph路径的输出和长度增长；改共享工作区才补并发/旁流覆盖。
- 实际生成后的下一轮新增输入、长短交替；涉及图片/工具或Hybrid状态时复验这些使用中的路径。
- 相同输入、长度、模型/草稿/K、精度、并发和缓存状态下，比较注意力总ms与完整轮ms；有效token/轮和任务吞吐成组记录。TPS变化伴随接受数变化时不能全归因kernel。

阶段5做足以判断实现正确、生效和收益方向的反馈，不给每个候选跑正式统计A/B；阶段8再集中做正式配对对标。小收益落在波动内则保留限定或不采用，不追到“物理极限”才允许继续。没有改善就保留原路径，并记录是并行度已足、归约抵消、带宽瓶颈、fallback未命中还是其他已观测原因；未知不要填成已定位。

最终交付长度到完整轮时的简表，注明实际快路径覆盖、缓存/显存变化及未验证范围。长注意力改善不能替代最后的真实任务质量验收，也不能承诺上下文增长完全不衰减。
