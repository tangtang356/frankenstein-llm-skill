# 缓存破坏专项：从真实续接到完整状态生命周期

用户反馈续问重算、生成内容接不上、读图/加载工具后命中骤降、摘要分叉或多会话互相冲掉缓存时读本章。它补充[上下文与缓存](context-and-cache.md)，直接处理已确认范围，不要求重跑全部部署阶段。具体历史根因、补丁入口、验收与未通过项见[缓存故障案例](cache-failure-cases.md)。

## 1. 先分清是哪一种缓存、丢了哪一段

“缓存”至少包含：前缀Attention KV；GDN/Mamba/卷积等可恢复状态；草稿或滑窗状态；图像上传引用、processor/encoder特征缓存；显存专家缓存；以及模板/分词/请求准备结果。CPU保存原始token不等于GPU仍有KV，图片特征命中也不等于整段多模态KV可恢复。应用直接返回旧答案更不是前缀复用。

按一次实际请求保存已有证据即可：request ID、入口与后端身份、前次实际输入token、实际生成token、本次实际输入token、停止原因、cached/新增计算、各组恢复边界、图像身份和服务端/客户端计时。原始日志留在部署目录，不把私有会话和图片传入技能仓库。先捕获失败现场，再做最小修复；不要一上来重启、清池，把原因和暖状态一起抹掉。

将“旧输入”“前次生成段”“本次新增工具结果/消息/图片”分别统计：

- `P`：上次真正送进runtime的输入token；`G`：该实现实际生成、交付/保留的token；`C`：本次runtime实际输入token。
- 依据后端终止与提交语义确定可比序列`H`。不要跨引擎硬套`P+G`或`P+G−1`：EOS、控制token、投机未接受行、最后一个待处理token可能不同。
- `L = LCP(H, C)`是相同token前缀长度。`L`到不了`P`尾部，先找旧输入变化；越过`P`但接不上`G`，查生成段重建和提交。
- `K`是实际恢复的共同有效边界。`L`足够大而`K`明显更早，转查各缓存组、检查点、回收与资源，不能继续把问题全归给模板。

在相同口径、同一身份且`C`确实延续`H`时，才将`L−K`解释为相同前缀中未恢复的部分；其中还要分合法块边界尾算与异常回退。`len(C)−L`是相对该前缀的新增/变化后缀，不自动等同“新增用户文本”。只有usage计数而缺原始token时只能估算，不能精确断言首差字符或根因。

**整轮命中率与旧前缀保留率分开。** 历史read工具回合命中3,772、增加946，整体仅79.95%，但旧前缀零丢失；相反某次旧前缀37,130退到33,083，而新增仅30，是实质回退。别只看一个百分比。

## 2. 快速按症状分流

| 观察 | 优先检查 | 不应直接得出的结论 |
|---|---|---|
| 新工具首次加入后，旧输入很早就不同 | 顶层tools/schema排序、系统消息插入位置、动态声明投影 | 新工具内容很长，所以旧历史理应全重算 |
| 每轮首差都在上次输入末端/思考开头 | `trim`、种子前缀、空格、换行、think边界 | 模型没有保存KV |
| 解码文字完全相同但token不同 | 非唯一分词、解码清理、重新encode | 模板文字相同就绝不丢缓存 |
| 只在工具调用后断开 | 原始流→parser→消息字段→模板的往返 | 一定是客户端或relay改写 |
| 追加图片后旧前缀很早变化 | 原图被替换/卸载、顺序/占位、processor参数 | 图片特征缓存命中就代表KV命中 |
| token完整保留但生成段重算 | EOS提交、生成检查点、FullAttention/GDN/SWA共同边界 | 再修一次token映射就够了 |
| 尾部快照存在，恢复失败或回退很深 | 前段KV依赖是否仍被引用，是否继续查较短快照 | 找到了快照对象就能恢复 |
| 相同prompt重放通过，真实生成续接失败 | SWA只保护原prompt窗口，生成窗口被优先复用 | 重复同一请求已证明多轮缓存正常 |
| 单会话好，A/B轮换或长短切换后差 | 缓存回收队列、总容量、草稿/Graph/专家竞争 | 无OOM、无抢占就没有缓存淘汰 |
| 摘要请求或压缩后首轮慢 | 分叉位置、历史锚点、摘要替换造成的真实前缀变化 | 所有压缩请求都应与原会话100%复用 |
| 高命中仍慢，或思考循环 | 模板/IPC/图片/调度/真实生成行为和计时口径 | 首响应长、模型反复说话就是缓存坏了 |

## 3. 输入身份：沿真实入口找第一个变化点

沿“应用历史 → SDK/relay请求 → 服务端模板 → tokenizer/多模态展开 → runtime token”逐层对齐。只查前端JSON不够，只用自己重写的模板也不够；离线复现应先能重建该次线上实际输入。保留custom messages、tool结果、思考字段和特殊token处理，否则诊断脚本自身可能插入占位结果，制造假差异。

### 动态工具、系统字段与恢复消息

检查工具新增、排序、schema序列化、时间/状态字段是否改写已缓存的前部。确有必要变化就如实接受失效，不冻结动态事实。底座支持时，可将新工具声明放在新增历史位置，同时让parser认识这些已授权声明；保留顶层旧表和历史顺序。需要确认该模型模板和parser支持，不能只把tools文字搬到user消息就宣称能力保留。

旧会话与新布局不强行混用。恢复提示应持久化并在固定历史位置重建，避免每轮临时插入不同前部；不擅自重写过去的思考/工具输出来刷命中。动态工具案例见C1。

### 空白、思考和生成种子

核对助手reasoning/content的前后空格、多换行、`</think>`、工具前分隔符、模板生成前缀。历史案例中`reasoning_content|trim`把两个空格变一个，使原输入最后一个token就失配；之后还发现`rstrip`后补换行、重复插入工具分隔符、误吞同文种子等不同分支。

修复被证实的字段往返，不对全部角色统一取消规范化。保留原思考、正文和工具语义；改变模板会改变部分旧会话的重建前缀，部署重启又会使驻留KV冷却，两种一次性代价要分别记录。早期`rstrip`单样本成功不能代表工具链和所有空白组合已修复。详见C2。

### 同文不同token，以及parser往返

生成token未必等于对同一文本重新encode的结果。比较token ID，并以关闭特殊token过滤/空白清理的decode核对完整文本。若是同文不同切分，可按现有实现保存有界的原生成token映射，在当前历史身份与解码文字严格一致时恢复原切分，再编码新增部分；同时检查模型/adapter、cache salt、模板/tokenizer及多模态映射的适用范围。

另一个分支是parser把原始输出归一化，例如正文与工具之间一个换行被重建为两个、JSON嵌套空格变化。此时“文本必须与原始流相同”的映射会漏掉。Strata/NInfer历史修复在**完整输出解析结束后**，用实际API返回的正文、思考和工具字段构建下一轮历史，并登记对应原生成token；匹配完整历史、plain/control语义及结束边界，不增加任意输出内部复用点。

这两种实现不能混用成“近似文字匹配就复用”。历史编辑、不同工具参数/顺序、改变思考保留方式、未完成输出和不支持的图片路径应按该实现正常失效/回退；不改parser语义、丢工具字段或补假EOS去通过匹配。只修token身份仍不证明实际KV状态存活。详见C3、C4、C8。

### 图片的两条验证链

第一条查上传/encoder复用：同图身份、处理参数、模型/processor版本是否一致，是否只处理新图。第二条查多模态KV：原图顺序、占位token与视觉展开位置、图片hash、实际恢复边界是否一致。不能只按文件名、URL或一串相同占位token认定图片相同；本次图片URL变化是否代表内容变化，要核对实际处理结果和缓存key。

生成token恢复改变长度时，也要校正后续新增图片的token偏移，逐图核对旧位置与完整占位范围。已经被替换成说明文字的旧图片不再是原来的模型输入。默认保留用户图片与可重建历史，不把删除旧图、改用旁路或另一个视觉模型当作通用缓存修复。若应用本来选择卸载/压缩，分别报告其语义变化与缓存代价。案例C5保留了早期旁路方案的局限。

## 4. 状态一致：所有必需缓存组在同一个边界恢复

先列出实际模型和草稿使用的组：FullAttention、GDN/Mamba/卷积、SWA、必要的页表/位置及检查点。记录每组在候选边界的查找结果和缺页，而非只打印每组“最大命中数”。**各组最大值的最小值不一定是共同可恢复边界**：检查点集合和窗口覆盖还要在同一位置一致。

### EOS、长度上限、拒绝与取消

对照实际提交行数、采样/交付行数、position、consumed/live、Target与draft状态、undo范围。IQ3曾在T=4的第一行遇到EOS，却先提交四行，续接只能回退；正确修复统一相关状态的有效前沿，不是仅裁掉输出文本。详情沿用[工程拆解第7节](optimization-engineering.md#7-生成结束后的缓存提交多少行就恢复多少行)。

取消/stop-string后的部分输出是否可恢复取决于实现：有完整保存协议才复用相应边界，否则只恢复已提交状态并计算必要尾部。不要把未接受的草稿、尚未交付的行或缺失状态伪装为完整历史。生成结束未产生新对齐快照时，合法尾算应解释而非一律判故障。

### 快照依赖、SWA窗口与回收顺序

- 快照必须拥有恢复所需的前段FullAttention页及尾部状态引用；LRU淘汰快照时一起释放。只保留尾state tensor会留下“对象存在、依赖已丢”的空壳。
- 最长快照失效时，释放孤立副本并继续查找较短候选，不能第一项失败就放弃所有可用前缀。
- SWA过期页不一定对未来请求无用：至少区分原prompt重放窗口和最新已提交生成检查点窗口。生成输出会成为下一轮输入，后者若被`reuse_first`优先覆盖，就会出现token完整却退回旧prompt的故障。
- 选择普通LRU优先级、有限引用保留或checkpoint策略时依现场原因决定，不无界pin所有页。历史SWA修复只改回收顺序，仍可淘汰，未扩大活跃块数；另一类快照依赖修复需要显式引用，二者不是同一补丁。
- 共享完成页、复制可写尾页；核对引用计数、copy-on-write、释放后泄漏、重复页。分配时既检查各组配额，也检查总空闲容量。所谓free pool可能包含可驱逐的暖缓存页，不表示这些页内容可永久保留。

细节和真实补丁入口见C7、C8；不能照抄另一版类名/函数签名。对象池、PromptPlan、Graph地址和状态ring改动还要查旧请求metadata及异步所有权，见[工程拆解](optimization-engineering.md)第6、8节。

## 5. 压缩、分叉与资源竞争

摘要生成请求可能回到较早历史前缀；只保留最新边界不一定覆盖它。使用少量与真实分叉有关的FullAttention/GDN/SWA对齐锚点，按实际密集增长节奏验证保留期限，不能用稀疏几轮回放代替多轮任务。锚点占用容量，应有界、有释放规则；六锚点历史案例不意味着所有机器都设六个。

压缩完成后用摘要替换旧历史，前缀本来可能变化；保留工具调用/结果配对、图片可用引用和用户要求比命中数字更重要。分别统计摘要请求、压缩后首轮、后续稳定续接。没有实际自然压缩样本时，只报告受控回放结果。

检查A→B→A、长→短→长、独立图片分支、新草稿滑窗、Graph/sampling工作区及专家驻留竞争。即使`max_num_seqs=1`、没有OOM/抢占，不同会话仍会先后驱逐缓存。容量扩容只用于证实的预算问题；先修依赖和回收逻辑，不能用更大池掩盖错误。详见C6、C9。

重启、模型/模板更换、cache salt改变、历史前部编辑造成的冷请求，单独标记。进程内KV不存在跨重启承诺时，重启后第一次慢不能证明补丁无效；同样不能把第一次加载后的“重复prompt命中”当成真实生成段续接验收。

## 6. 验收覆盖按改动选，不再只测重复prompt

每次缓存修复至少保留一个原故障复现和一条相关的真实生成续接；下表按触及路径补充，短阶段可用短例，长专项默认约10k起步，不强制所有修改运行全部长场景。

| 改动触及 | 有意义的验证 |
|---|---|
| 模板/分词/工具parser | 实际生成→工具执行→回传→续问；空白、中文/引号/嵌套参数；修改历史后正确失效 |
| 动态工具/恢复投影 | 首次新增当轮就保留旧前缀；真实调用新增工具；后续投影稳定；旧会话不被强迁移 |
| EOS/投机状态 | 自然EOS、长度结束及实际尾宽；只在实现涉及时补拒绝/取消恢复；比对提交与下一轮恢复 |
| Hybrid/快照/SWA回收 | 每组同边界；缺失最长候选后较短回退；真实生成跨checkpoint后续接；引用释放与总容量 |
| 图像身份/偏移 | 旧图重复、追加新图、换旧图/调顺序；分别查encoder和KV，检查模型是否真的看到正确图 |
| 资源/锚点/并发 | 独立前缀A/B交替、长短切换和实际分叉；需要自然压缩时跟随用户任务，不另起业务任务制造样本 |

同条件比较实际新计算量、服务端TTFT、客户端首模型内容和整次任务时间；输出正确性独立检查。较低命中率可能只是新工具结果变长，高命中仍可能有CPU/IPC延迟。冷热图像回答都错且输出一致，不能据此说缓存造成误读；缓存计数通过也不代表OCR正确。

完成后写清：具体触发行为、首差或首个缺失依赖、修改入口与已加载版本、原故障前后结果、相关功能、未测项、正常尾算/容量界限。修复代码、离线样本、实际KV命中、真实任务完成分别表述；不以“缓存开关已开”“百分比接近100%”替代这些证据。

公共机制参考：[vLLM前缀缓存设计](https://docs.vllm.ai/en/stable/design/prefix_caching/)说明block身份包含父前缀、实际token和必要的多模态/adapter/salt信息。它解释机制，不证明本章私人历史成绩；现场仍以安装版本和真实请求为准。
