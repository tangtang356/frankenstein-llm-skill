# 专家供给、计算与状态调度的实施方法

按当前瓶颈读取对应节；配套[推进顺序](case-swift-iq3xxs-python.md)与[毫秒实施](millisecond-case-lessons.md)。参数从目标模型的实际格式、shape和资源预算确定。

## 1. 把配置、实际分支和执行成本连起来

先回答三个问题：请求经过哪条路径？时间花在哪里？下一项修改能消除哪段工作？

| 现场现象 | 优先查看 | 对应行动 |
|---|---|---|
| 开了双窗口，轮时仍接近串行 | 请求惩罚、草稿位置、流水线分支及Graph回退日志 | 先接通实际并行路径 |
| 专家CPU项大、GPU等待多 | 路由命中、未命中去向、缓存适配与RAM供给 | 组合优化驻留、内存布局和交换 |
| 专家高命中，且供给/传输等待已确认不再占主要成本，短轮仍慢 | 命中专家计算、投影、草稿链、状态提交 | 转向实际shape的计算和复制；若供给等待尚未查清，继续检查真实搬运、预取和阻塞 |
| 两卡验证时间接近，速度仍不理想 | 草稿与主模型共卡的竞争、两段启动时序 | 按整条流水线重新分工 |
| Decode快，但续问又读大量正文 | 生成token、EOS/长度提交、Hybrid检查点 | 修正状态边界和前缀续接 |
| 命中正常，短续问仍有固定等待 | 检查点分配/保存、图片、模板及请求准备 | 去掉重复分配和准备 |

先修真实请求导致的串行或回退分支，再选择局部算子。读取分支条件后，用实际请求确认命中。

## 2. 专家缓存：先让需要的专家及时到位

### 看清三个层次

- **驻留容量**：显存实际容纳多少专家、占多少字节。
- **路由命中**：这一请求真正访问的专家有多少在显存。
- **未命中成本**：剩余工作是CPU计算、RAM到GPU搬运，还是需要读盘。

先核对请求增量。若稳定请求文件读取为0，而CPU专家工作仍大，就应查RAM/CPU供给与驻留，而不是继续调磁盘预取。若热点专家没有被适配进显存，先让现有适配机制真正工作。

驻留适配发布需有事件边界，等旧消费者与相关复制完成后更新映射；供给负担降低后再查剩余计算。

### 把缓存和供给作为配套组合

供给优化按依赖组成可运行的组合：

1. **大页RAM布局**：专家补集arena按系统支持的大页尺寸对齐，在首次触页前请求THP，沿用分步CUDA注册。检查实际大页使用量，避免只写开关却仍全部4KiB页。
2. **交换缓冲轮换**：按权重块尺寸复用交换缓冲，通过所有权轮换避免把淘汰专家再完整复制进另一个槽。
3. **更及时的驻留适配**：调整驻留适配间隔时，同步按周期比例重算热度衰减；若原间隔为I、衰减为d，新间隔为J，可用d^(J/I)保持每轮衰减速度。
4. **沿原事件边界发布**：旧窗口读完旧专家、相关复制结束后，再发布新槽位映射；把“开始搬运”和“消费者可以使用”分清。

分别记录供给成本、暴露等待与完整轮变化；不要因单个部件暂未改善就提前否定依赖它的完整组合。

CPU工作成本变化后，重新比较CPU直接计算与准备＋传输＋设备计算＋排队。根据实际shape选未命中分担，设备算得快不代表搬过去更划算。

## 3. 显存预算：先装完整，再提高有效驻留

把显存拆成主模型常驻部分、专家缓存、草稿、KV、Hybrid状态/快照、Graph工作区和视觉。先完成加载和Graph捕获，再看余量及实际供给表现。

显存预算以模型加载、Graph捕获和实际短通路之后的峰值与余量为准。驻留容量须与KV、草稿和视觉共同安排，不追求单项最高占用。

需要增加驻留时，先找重复权重副本、过大的临时缓冲和不必要的常驻对象。若改变KV/草稿/视觉预算，回到整套方案一起处理。进入长上下文阶段后再观察KV增长是否挤压专家，避免用短任务分配直接推断长任务表现。

## 4. 目标设备计算：从真实权重和shape决定适配

### 先做一张实际算子表

只列正在走的主要矩阵：Target专家gate/up/down、共享专家、注意力/GDN投影、MTP投影、输出头。每项记录格式、输入/输出维度、每次处理行数T、所在GPU及实际kernel。

逐tensor核对真实混合格式，预打包只对适用矩阵启用，额外数据计入预算；不能给整个模型统一套同名开关。

### 针对实际布局复用已有实现

用实际专家尺寸、格式配对、行数与路由测试已有布局，采用匹配目标硬件的实现。

实施时优先复用已有bench、生产函数和Graph路径。确认真实格式、shape、索引和输出，再把匹配分支接入运行器。新分派尽量窄，只覆盖确实合适的形状；其他矩阵继续走原有实现。

### 输出头要按真实草稿链查

对异步草稿链分段计时，确定输出头、投影、专家还是等待占主导；不要默认专家计算就是大头。

对真实输出头形状调整warp分工和共享方式，保持原数学、归约与完整词表；检查局部成本能否兑现为完整轮收益。

## 5. 多卡流水线：把草稿、验证和交接一起配平

先画当前实现中真实重叠的几段：草稿链、Target前段、Target后段、状态提交和下一窗口准备。只画实际依赖，不按模型层数平均分配时间。

**草稿所在卡也承担工作。** 按草稿、验证与共享资源的实际耗时分配层/阶段，层数对称不等于负载平衡。微调后看完整请求，不能只看两段耗时更接近。

**先提交已经就绪的工作。** 当前段完成，先把后段入队，再服务其他窗口和准备下一草稿，减少两卡之间的空隙。检查同一主机循环是否等待一个结果时停止推进另一卡。

**把真正独立的投影放到旁分支。** 仅读取本层输入的门控/查询投影可接现有fork/join，在真实依赖满足后汇合。

定位间隙时区分“GPU工作尚未完成”和“已完成但主机尚未发现”。后者已很小时，不继续优化轮询；转查图内计算与共享资源竞争。埋点必须覆盖实际异步链。

## 6. GDN快照：通过状态版本轮换减少复制

双窗口投机需要能回到正确的GDN/卷积状态。普通做法会复制快照，再在拒绝时恢复；如果每轮都复制大块状态，固定成本会积累。

该路径使用会话状态和现有快照缓冲组成ring：

1. Graph通过设备上的当前指针读取本轮状态。
2. 提交根据源/目标槽选择，从源状态计算到目标状态，保存源版本供可能的undo使用。
3. 提交完成后更新当前指针；接受时继续使用新版本，拒绝时回到对应有效版本。
4. 缓冲再次轮换前确认旧消费者已结束；保持状态内容、有效行数和位置一起前进。

通过版本轮换减少额外整块复制，保持旧状态供拒绝/撤销使用；最后测完整轮净收益，不能省掉必要状态或放弃回滚。

实现时沿用现有提交内核的数学计算，重点检查跨缓冲提交、自然回滚、EOS/长度结束与下一请求续接。Graph捕获前准备稳定的表和指针，运行时更新选择，避免把某次固定槽位错误地固化到Graph里。

生成段或长思考续接问题还需联合检查[思考往返、快照与回收生命周期](reasoning-prefix-cache.md)；token一致和快照对象存在都不是充分条件。

## 7. 生成结束后的缓存：提交多少行就恢复多少行

一个验证窗口可能在前几行已遇到EOS或输出长度边界。若先提交全部行再裁返回文本，内部状态会多走，下一请求只能回退。

修复方式是在提交前算出EOS/输出长度对应的有效输入行数，并统一用于：

- 后段Target提交；
- consumed/live前缀与位置更新；
- 前段状态提交；
- 已提前运行的推测窗口undo。

沿用原GDN/卷积、QSA索引和其他状态恢复逻辑，而不是只裁剪输出token列表。修复后核对实际共同前缀和新处理后缀，确认不再因多提交而回退。

可复用的排查顺序是：对齐真实输入和生成token → 找到第一个不一致位置 → 核对该位置的提交/停止/检查点边界 → 修正所有相关状态的共同前沿。不要先扩大缓存池来掩盖错误提交。

## 8. 短续接：把固定准备开销移出请求热路径

缓存已经复用时，请求仍可能花时间分配检查点、注册/准备主机缓冲或重复构建计划。先分开“分配空白存储”和“保存当前内容”。

可复用内存池、按依赖并行保存和预分配空白检查点缓冲，减少分配/初始化；每次仍写入当前真实状态。分别测保存成本与正常续接请求，不能把存储复用误写成状态内容跨请求可复用。

缓冲复用时同时清理与上一请求绑定的计划和metadata。该路径补齐了回收时旧PromptPlan清理，避免新请求使用旧分块计划。对对象池的检查应包含“存储可以复用，旧请求语义必须重置”。

## 9. Prefill专项：减少重复搬运，再看适合的计算路径

进入主流程的prefill阶段后，先确认真实格式和所走分支。可按实际成本选择以下实现：

- **固定投影路径**：按实际运算与shape选择相容实现，确认分派并比较完整输入处理时间。
- **MMQ驻留专家直接读取**：沿用整数MMQ和原专家顺序，通过指针表直接使用已驻留权重，减少重复gather；配套覆盖两卡驻留与流式供给路径。

优先查同一数据是否被反复转换、gather或搬运，再选择适合shape的融合。部署新分块或供给环时把消费者所需的阈值、槽位和生命周期一起接通。一个新内核若配套不完整，单独打开开关并不能代表它的完整能力。

## 10. 组合推进与跨模型继承

组合的部件不必来自同一仓库。宿主保留服务与状态协议，来源可以贡献量化内核、通信、注意力或视觉子系统；跨模型先匹配数学运算、实际shape和数据表示，再适配调用者。具体区分直接移植与机制借鉴，见[跨仓库组合](cross-repository-composition.md)。

把改动按依赖分成能实际运行的组合：

| 组合 | 主要内容 | 下一步依据 |
|---|---|---|
| 供给组合 | RAM布局、专家驻留/交换、CPU/GPU成本、搬运重叠 | CPU供给与暴露等待下降后，查剩余GPU热点 |
| 计算组合 | 真实shape布局、草稿投影、输出头 | 计算改善后，重新看两卡竞争与交接 |
| 调度与状态组合 | 工作分工、独立分支、及时提交、快照轮换 | 完整轮时和短续接正常后进入长任务 |
| 长上下文与续接 | [长注意力专项](long-attention-optimization.md)、终止提交、检查点、请求准备 | 冷/复用/新增输入分别解释，再接常用任务 |

前期每个完整组合做必要短计时和受影响功能检查，正式A/B仍留在主流程最终对标阶段。不要为每个开关排列组合，也不要在组件尚缺依赖时就宣判整条路线失败。

迁移到不同模型或量化时，把已有改动分成三类：

- **可复用机制**：流水线交接、状态轮换、终止提交、请求准备。
- **需要重新匹配的实现**：专家量化配对、矩阵shape、草稿头/词表、MMQ和投影分派。
- **需要重新分配的资源**：专家与RAM补集、草稿占用、KV/状态池、Graph和工作区。

保留已接受的源码、编译库和配置组合；迁移后确认实际加载。不同阶段或工作量的读数不能反推为某一补丁的独立收益。

## 11. 实际工作时怎么记

在项目已有说明里，用五句话即可承接下一轮：

> 当前基准任务约多少ms；主要时间落在哪条实际路径。已完成什么配套组合，为什么会减少工作。下一步只处理哪个剩余成本。短续接与受影响功能有什么结果。当前使用哪个构建/配置，未完成工作是什么。

直接使用原生日志和现有脚本。基础测试可复用[Python基准题](../assets/python-round-baseline.md)；常态轮时、短时最低轮时和吞吐峰值分列。详细计时定义见[测量契约](measurement-contract.md)，完整阶段顺序见[主入口](../SKILL.md)。
