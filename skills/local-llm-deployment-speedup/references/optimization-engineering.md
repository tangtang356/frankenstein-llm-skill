# 从IQ3优化路径提炼的实施方法

配合[完整案例](case-swift-iq3xxs-python.md)使用：案例按时间讲数值，本篇按问题讲怎样定位、修改和推进。下列参数是该路径的实现示例；在目标版本核对对应代码后使用。按实际瓶颈读相关章节，不要求从头逐项尝试。

## 1. 把配置、实际分支和执行成本连起来

先回答三个问题：请求经过哪条路径？时间花在哪里？下一项修改能消除哪段工作？

| 现场现象 | 优先查看 | 对应行动 |
|---|---|---|
| 开了双窗口，轮时仍接近串行 | 请求惩罚、草稿位置、流水线分支及Graph回退日志 | 先接通实际并行路径 |
| 专家CPU项大、GPU等待多 | 路由命中、未命中去向、缓存适配与RAM供给 | 组合优化驻留、内存布局和交换 |
| 专家高命中，且供给/传输等待已确认不再占主要成本，短轮仍慢 | 命中专家计算、投影、草稿链、状态提交 | 转向实际shape的计算和复制；若供给等待尚未查清，继续检查真实搬运、预取和阻塞 |
| 两卡验证时间接近，速度仍不理想 | 草稿与主模型共卡的竞争、两段启动时序 | 按整条流水线重新分工 |
| Decode快，但续问又读大量正文 | 生成token、EOS/长度提交、Hybrid检查点 | 修正状态边界和前缀续接 |
| 命中正常，短续问仍有固定等待 | 检查点分配/保存、图片、模板及请求准备 | 去掉重复分配和准备 |

案例最初52.58ms的请求实际因为重复惩罚走串行。先修请求分支比立刻重写一个小算子有效。阅读对应源码的分支条件，再用一次真实请求确认命中；不要只根据配置项存在来判断实现已生效。

## 2. 专家缓存：先让需要的专家及时到位

### 看清三个层次

- **驻留容量**：显存实际容纳多少专家、占多少字节。
- **路由命中**：这一请求真正访问的专家有多少在显存。
- **未命中成本**：剩余工作是CPU计算、RAM到GPU搬运，还是需要读盘。

先核对请求增量。若稳定请求文件读取为0，而CPU专家工作仍大，就应查RAM/CPU供给与驻留，而不是继续调磁盘预取。若热点专家没有被适配进显存，先让现有适配机制真正工作。

IQ3_XXS阶段采用有事件栅栏的专家缓存适配，Python命中升至99.0%，轮时37.52→25.81ms。此时供给负担已经明显减少，后续才把重点移向SM75专家计算和草稿头。

### 把缓存和供给作为配套组合

IQ3_S阶段的实际组合包括：

1. **大页RAM布局**：专家补集arena按2MiB对齐，在首次触页前请求THP，沿用分步CUDA注册。检查实际大页使用量，避免只写开关却仍全部4KiB页。
2. **交换缓冲轮换**：按权重块尺寸复用交换缓冲，通过所有权轮换避免把淘汰专家再完整复制进另一个槽。
3. **更及时的驻留适配**：间隔由16轮改为4轮，同时把每次衰减从0.7改为`0.7^(4/16) ≈ 0.914691`，保留按轮次计算的热度衰减速度。
4. **沿原事件边界发布**：旧窗口读完旧专家、相关复制结束后，再发布新槽位映射；把“开始搬运”和“消费者可以使用”分清。

这组配套使Python28.88→25.45ms，专家命中91.2%→96.0%，CPU累计项13.47→7.80ms/轮。应检查完整组合，不因大页或交换单独一项暂未改善就提前放弃依赖它的后续方案。

如果CPU工作成本变了，原来的CPU/GPU未命中分担比例也要重新评估。比较的是**CPU直接计算**与**准备＋传输＋GPU计算＋排队**的实际成本。案例某些单专家形状中，复制加GPU为139～188µs，CPU冷缓存池为104～118µs，因此没有继续增加GPU分担。GPU算得快不等于搬过去更快。

## 3. 显存预算：先装完整，再提高有效驻留

把显存拆成主模型常驻部分、专家缓存、草稿、KV、Hybrid状态/快照、Graph工作区和视觉。先完成加载和Graph捕获，再看余量及实际供给表现。

案例曾以较小预留扩大专家缓存，但首卡Graph捕获后只余348MiB；最终用800/800MiB预留，专家驻留21128对，余量约548/663MiB，保留完整KV容量与视觉能力。方法是找**可稳定运行且供给成本低**的分配，而不是固定追求最高显存占用。

需要增加驻留时，先找重复权重副本、过大的临时缓冲和不必要的常驻对象。若改变KV/草稿/视觉预算，回到整套方案一起处理。进入长上下文阶段后再观察KV增长是否挤压专家，避免用短任务分配直接推断长任务表现。

## 4. SM75计算：从真实权重和shape决定适配

### 先做一张实际算子表

只列正在走的主要矩阵：Target专家gate/up/down、共享专家、注意力/GDN投影、MTP投影、输出头。每项记录格式、输入/输出维度、每次处理行数T、所在GPU及实际kernel。

Swift的Target是混合IQ/K，HC为BF16，输出头Q5_K；草稿里才有四块适合Q8预打包的投影。因此Q8优化只应用于实际Q8矩阵，约增加15.9MiB打包数据，而不是给整个主干套用同名开关。

### 针对实际布局复用已有实现

该模型专家H=2560、FF=640、每层512专家，gate/up与down包含10组格式配对。用真实权重和实际T/路由形状比较已有布局后，采用SM75 mode8；Python25.60→23.28ms。

实施时优先复用已有bench、生产函数和Graph路径。确认真实格式、shape、索引和输出，再把匹配分支接入运行器。新分派尽量窄，只覆盖确实合适的形状；其他矩阵继续走原有实现。

### 输出头要按真实草稿链查

异步MTP诊断发现每步头GEMV约0.363～0.365ms，链累计约2.48ms，约占所测草稿链35%；专家计算反而只有约0.054～0.058ms/步。所以下一步选Q5_K输出头，而不是继续优化已很小的草稿专家。

针对2560×106299、T1的真实草稿头，用单个物理warp模拟原四warp的局部和与归约顺序，减少协作开销。两卡头微测约0.374→0.327ms、0.381→0.350ms；对应阶段Python23.28→22.88ms。无需缩词表、改权重精度或重新训练草稿。

## 5. 双卡流水线：把草稿、验证和交接一起配平

先画当前实现中真实重叠的几段：草稿链、Target前段、Target后段、状态提交和下一窗口准备。只画实际依赖，不按模型层数平均分配时间。

**草稿所在卡也承担工作。** 案例MTP在GPU0，24/24层看似对称，却让GPU0同时承担草稿。调整到22/26后，草稿链主机观测约7.66→7.02ms，暖态Python168.74→170.43 tok/s。23/25虽然两卡验证更接近，也未给出更快的完整请求。

**先提交已经就绪的工作。** 当前段完成，先把后段入队，再服务其他窗口和准备下一草稿，减少两卡之间的空隙。检查同一主机循环是否等待一个结果时停止推进另一卡。

**把真正独立的投影放到旁分支。** GDN门控与QSA查询链中只读本层输入的工作可复用现有fork/join，在依赖满足后汇合；案例采用独立投影分支后Python达到22.24ms。

定位间隙时分开“GPU工作尚未完成”和“已完成但主机尚未发现”。案例后期两者就绪到下一窗口启动仅约0.15ms，单纯提前轮询没有收益；此时更值得查图内计算和共享GPU资源竞争。计时手段应覆盖实际异步链，而不是只给未被调用的同步接口打点。

## 6. GDN快照：通过状态版本轮换减少复制

双窗口投机需要能回到正确的GDN/卷积状态。普通做法会复制快照，再在拒绝时恢复；如果每轮都复制大块状态，固定成本会积累。

该路径使用会话状态和现有快照缓冲组成ring：

1. Graph通过设备上的当前指针读取本轮状态。
2. 提交根据源/目标槽选择，从源状态计算到目标状态，保存源版本供可能的undo使用。
3. 提交完成后更新当前指针；接受时继续使用新版本，拒绝时回到对应有效版本。
4. 缓冲再次轮换前确认旧消费者已结束；保持状态内容、有效行数和位置一起前进。

这样减少了为了保留旧状态而额外做的整块快照复制，Python完整轮次21.1174→20.8037ms。这里的重点是**改变状态保存方式**，不是省掉必要状态或放弃回滚。

实现时沿用现有提交内核的数学计算，重点检查跨缓冲提交、自然回滚、EOS/长度结束与下一请求续接。Graph捕获前准备稳定的表和指针，运行时更新选择，避免把某次固定槽位错误地固化到Graph里。

## 7. 生成结束后的缓存：提交多少行就恢复多少行

一次100K任务末窗口T=4、全部草稿通过，但第一个Target输出已经是EOS。旧路径先提交4行，再按EOS停止输出，内部状态多走了3行。下一请求完整前缀对不上，只能退回较早检查点，重读约1391个正文token。

修复方式是在提交前算出EOS/输出长度对应的有效输入行数，并统一用于：

- 后段Target提交；
- consumed/live前缀与位置更新；
- 前段状态提交；
- 已提前运行的推测窗口undo。

沿用原GDN/卷积、QSA索引和其他状态恢复逻辑，而不是只裁剪输出token列表。修复后相应100K续问只处理33个新增token，首响应约0.4秒。

可复用的排查顺序是：对齐真实输入和生成token → 找到第一个不一致位置 → 核对该位置的提交/停止/检查点边界 → 修正所有相关状态的共同前沿。不要先扩大缓存池来掩盖错误提交。

## 8. 短续接：把固定准备开销移出请求热路径

缓存已经复用时，请求仍可能花时间分配检查点、注册/准备主机缓冲或重复构建计划。先分开“分配空白存储”和“保存当前内容”。

案例启用内存池、双卡保存与检查点空白缓冲预分配，诊断保存时间从约65～70ms降到约12～18ms；每次仍保存真实当前状态。最终无诊断版本的1543/290/56输入处理分别记录为2333/934/415ms。这是续接准备方面的改进，单独统计。

缓冲复用时同时清理与上一请求绑定的计划和metadata。该路径补齐了回收时旧PromptPlan清理，避免新请求使用旧分块计划。对对象池的检查应包含“存储可以复用，旧请求语义必须重置”。

## 9. Prefill专项：减少重复搬运，再看适合的计算路径

进入主流程的prefill阶段后，先确认真实格式和所走分支。案例两项实现：

- **固定HC投影路径**：针对实际HC运算使用合适的SM75计算路径，Python冷prefill曾1800.4→1665.9ms，Three.js2003.2→1886.1ms。
- **MMQ驻留专家直接读取**：沿用整数MMQ和原专家顺序，通过指针表直接使用已驻留权重，减少重复gather；配套覆盖两卡驻留与流式供给路径。

优先查同一数据是否被反复转换、gather或搬运，再选择适合shape的融合。部署新分块或供给环时把消费者所需的阈值、槽位和生命周期一起接通。一个新内核若配套不完整，单独打开开关并不能代表它的完整能力。

## 10. 组合推进与跨模型继承

把改动按依赖分成能实际运行的组合：

| 组合 | 主要内容 | 下一步依据 |
|---|---|---|
| 供给组合 | RAM布局、专家驻留/交换、CPU/GPU成本、搬运重叠 | CPU供给与暴露等待下降后，查剩余GPU热点 |
| 计算组合 | 真实shape布局、草稿投影、输出头 | 计算改善后，重新看两卡竞争与交接 |
| 调度与状态组合 | 工作分工、独立分支、及时提交、快照轮换 | 完整轮时和短续接正常后进入长任务 |
| 长上下文与续接 | 注意力、终止提交、检查点、请求准备 | 冷/复用/新增输入分别解释，再接常用任务 |

前期每个完整组合做必要短计时和受影响功能检查，正式A/B仍留在主流程最终对标阶段。不要为每个开关排列组合，也不要在组件尚缺依赖时就宣判整条路线失败。

迁移IQ3_XXS → IQ3_S → IQ3_XXS时，把已有改动分成三类：

- **可复用机制**：流水线交接、状态轮换、终止提交、请求准备。
- **需要重新匹配的实现**：专家量化配对、矩阵shape、草稿头/词表、MMQ和投影分派。
- **需要重新分配的资源**：专家与RAM补集、草稿占用、KV/状态池、Graph和工作区。

保留已接受的源码、编译库和配置组合；迁移后先确认实际加载了这些实现。案例结果与本篇方法相连，不能把最终18ms或220+峰值反推为某一个补丁的单独收益。

## 11. 实际工作时怎么记

在项目已有说明里，用五句话即可承接下一轮：

> 当前Python约多少ms；主要时间落在哪条实际路径。已完成什么配套组合，为什么会减少工作。下一步只处理哪个剩余成本。短续接与受影响功能有什么结果。当前使用哪个构建/配置，未完成工作是什么。

直接使用原生日志和现有脚本。基础测试可复用[历史Python题](../assets/python-round-baseline.md)；常态轮时、短时最低轮时和吞吐峰值分列。详细计时定义见[测量契约](measurement-contract.md)，完整阶段顺序见[主入口](../SKILL.md)。
